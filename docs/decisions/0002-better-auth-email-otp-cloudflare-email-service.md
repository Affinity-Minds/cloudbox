# ADR 0002 — Email OTP authentication via Better Auth and Cloudflare Email Service

**Status:** Proposed  
**Date:** 2026-09-26  
**Context:** Slice 1.1 implementation  
**Stakeholders:** WT-0, WT-1 (Auth)

## Problem

CloudBox SaaS needs secure human authentication for Super Admin and staff. Requirements:
- No custom auth code (use maintained libraries)
- Email-based OTP for passwordless access
- Verified sending domain (avoid spam folders)
- Dev echo mode for local testing (OTP_DEV_ECHO=1)
- Rate limiting and anti-enumeration

## Decision

**Use Better Auth `emailOTP` plugin with Cloudflare Email Service.**

1. **Better Auth (v1.7.6+):** Maintained passwordless auth library with Drizzle D1 adapter. Provides OTP generation, storage, rate limiting, session management (httpOnly cookies).

2. **Cloudflare Email Service:** Binding named `EMAIL` in `wrangler.jsonc`. Sends domain `em.affinity.ai.in` (verified in Cloudflare account with SPF, DKIM, DMARC records).

3. **From address:** `no-reply@em.affinity.ai.in`

4. **Provider verification:** The account that owns the `cloudbox` Worker must have:
   - `affinity.ai.in` zone onboarded
   - Email Sending enabled and configured
   - `soren@affinityminds.net` added as verified destination (or broader Paid plan)

5. **Dev mode:** `OTP_DEV_ECHO=1` in `.env.development` prints OTP to console; production never echoes.

## Alternatives considered

- **Resend:** Third-party SaaS email provider (introduces external dependency, billing, API key rotation)
- **SMTP relay:** Requires external mail server setup (added operational complexity)
- **Custom OTP + email:** Not an alternative (violates "no custom auth code" rule)

## Consequences

**Positive:**
- No custom OTP code; rely on maintained library updates
- Sending domain verifiable and high deliverability
- OTP visible locally during dev; no email setup needed for testing
- Cloudflare binding reduces external dependencies

**Risks:**
- **Account mismatch:** If `affinity.ai.in` and Email Sending are in different Cloudflare accounts, send throws `E_SENDER_NOT_VERIFIED`. Mitigation: owner must verify during bootstrap.
- **Delivery failure:** If verified destination list is full, arbitrary address sends may fail. Mitigation: explicitly add target addresses or use Paid plan; keep error message user-friendly.
- **Rate limits:** Better Auth applies 6 sends/hour per email + 3 verify attempts/OTP. Validate these limits with owner before launch.

## Implementation notes

- Better Auth schema generated by `@better-auth/cli` during foundation commit
- Adapter in `src/auth/email.ts` wraps `env.EMAIL.send()`
- OTP template: plain text or HTML email (to verify with owner)
- Session: httpOnly + Secure cookie, 7-day TTL (to verify)
- Audit events: `OTP_SENT`, `OTP_VERIFIED`, no secrets logged
