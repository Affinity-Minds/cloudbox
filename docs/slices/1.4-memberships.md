# Slice 1.4 — Memberships

## Goal

A user can belong to multiple tenants with different standing levels (Owner, Admin, User). When a user selects a tenant, all subsequent requests are scoped to that tenant. Cross-tenant data leakage is impossible.

## Existing capabilities reused

- `tenant_memberships` table from foundation migration 0003
- Tenant selection in UI (TanStack Router navigation + state)
- `requireTenantStanding('owner'|'admin'|'user')` middleware
- Session management from Slice 1.1
- Audit service for membership changes

## Data changes

**Schema (from foundation migration 0003):**
- `tenant_memberships(id PK, tenant_id FK→tenants.id, user_id FK→user.id, standing CHECK('owner','admin','user'), status CHECK('active','revoked'), invited_by, created_at, UNIQUE(tenant_id,user_id))`

**Active tenant selection:**
- Session extended with `active_tenant_id` (stored server-side or in JWT if stateless architecture)
- User can switch tenants via menu/dropdown
- All subsequent queries filtered by active_tenant_id

## Authorization

- Permission: `tenant_membership.view`, `tenant_membership.invite`, `tenant_membership.revoke`
- Only Tenant Owner can invite/revoke members
- Users may only see memberships for tenants they belong to

## Audit events

- `MEMBERSHIP_INVITED` — tenant_id, invitee_email, invited_by, standing, timestamp
- `MEMBERSHIP_ACCEPTED` — tenant_id, user_id, timestamp (if email acceptance flow)
- `MEMBERSHIP_REVOKED` — tenant_id, user_id, revoked_by, timestamp
- `TENANT_SWITCHED` — user_id, old_tenant_id, new_tenant_id, timestamp

## Tests

**Happy path:**
- Owner invites user to Tenant A
- User receives invite (if email), or sees invite in UI
- User accepts/joins
- User switches to Tenant A (selects from list)
- User can view Tenant A's devices and subscriptions
- User switches back to Tenant B
- Verify Tenant B data visible, Tenant A data hidden

**Permission boundaries:**
- Non-Owner cannot invite members
- User in Tenant A cannot see Tenant B members or data
- Revoked member cannot access Tenant A anymore

**Tenant isolation (hard test):**
- User A (Tenant A) attempts API call with Tenant B ID in route
- Server returns 403 (not leaked 404, not partial data)

## Demo path

```
1. Log in as User A (Tenant A Owner)
2. Navigate to Members
3. Click "Invite Member"
4. Enter "user-b@example.com", standing="admin"
5. Submit
6. Open new session as User B
7. See invitation (or access if auto-added)
8. Verify User B sees Tenant A in "My Tenants" list
9. Click switch to Tenant A
10. Verify User A's devices/data visible
11. Verify audit events: MEMBERSHIP_INVITED, MEMBERSHIP_ACCEPTED, TENANT_SWITCHED
```
