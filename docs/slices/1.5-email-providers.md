# Slice 1.5 — Email provider registry with SMTP and fallback

## Goal

The console can configure N email providers (Cloudflare Email Service binding, SMTP, or a
development-only log provider), order them by priority, test each one, and every send tries them
in order until one succeeds — with zero providers configured falling back to the pre-existing
`EMAIL` binding so nothing regresses for an install that never touches this screen.

## Existing capabilities reused

- `worker-mailer` (npm) for SMTP over `cloudflare:sockets` — no custom MIME/SASL/TLS code.
- `crypto.subtle` (AES-256-GCM) for the SMTP password envelope — no custom crypto.
- `@hono/zod-validator` + Zod discriminated unions for request validation.
- `requirePermission("settings.manage")` (WT-1's real middleware) on every route.
- `audit()` (WT-0) for every consequential write.
- shadcn `sheet` + `field`, `react-hook-form` + `@hookform/resolvers/zod` for the add/edit form.
- `@tanstack/react-query` for the list/mutations, `sonner` for toasts — the same stack every other
  screen in `apps/admin-web` uses.

## Data changes

**Migration:** `0008_email_providers.sql` — table `email_providers(id, name, kind, priority,
enabled, from_address, config_json, secret_ciphertext, secret_iv, updated_by, created_at,
updated_at)`. Drizzle table in `apps/worker-api/src/email/providers/schema.ts` (not `db/schema.ts`
— see the ADR and the handoff's "Requests to WT-0").

## Authorization

Every route (`GET/POST /`, `PATCH/DELETE /:id`, `POST /:id/test`) requires the `settings.manage`
staff permission. Per the seeded catalogue (migration `0003`), only `super_admin` and `admin`
hold it; `support` and `read_only` get `403`, unauthenticated requests get `401` — verified both
by dedicated tests and by the repo's self-discovering permission-boundary matrix
(`test/permission-matrix.test.ts`), which enumerates every `/api/v1` route automatically.

## Audit events

- `EMAIL_PROVIDER_CREATED` / `EMAIL_PROVIDER_UPDATED` / `EMAIL_PROVIDER_DELETED` — before/after are
  the masked provider shape (`hasSecret` boolean only, never the ciphertext or plaintext).
- `EMAIL_PROVIDER_TESTED` — outcome of a `POST /:id/test` call, actor is the staff member who
  clicked it.
- `EMAIL_SENT` / `EMAIL_FAILED` — one row per provider attempt inside `sendEmail()`, carrying
  `{purpose, providerId, kind, messageId}` or `{purpose, providerId, kind, errorCode}`. Never the
  message body, never a secret.

## Tests

**Happy path:** create each kind; SMTP round-trips its secret through AES-256-GCM and `GET` never
returns it; reorder via `PATCH priority`; enable/disable; test-send reports the outcome; delete.

**Fallback and ordering:** zero providers configured falls back to the `EMAIL` binding
(`sendEmail` unit test); a failing provider is audited and skipped, the next one (by priority) is
used and also audited (`email-send.test.ts`).

**Permission boundaries:** `401` unauthenticated, `403` for `read_only`
(`email-providers.test.ts`, plus the repo-wide self-discovering matrix).

**Failure paths:** `503 provider_secrets_key_missing` when `PROVIDER_SECRETS_KEY` is unset and a
secret is being saved; `409 last_enabled_provider` deleting (or disabling, an extension beyond the
literal brief) the only enabled provider; `400 log_provider_disabled_in_production` for the `log`
kind outside development.

## Demo path

```
1. Settings → Email providers → "No providers configured; the Cloudflare Email binding is used."
2. Add provider → SMTP → smtp.mx.cloudflare.net:587, a username/password → Save
3. Row appears, priority 100, enabled, "not tested"
4. Click the send icon → row shows "sent" or the relay's error code
5. Add a second provider with a lower priority number → use the ↑ arrow to reorder
6. Disable the first provider → try to delete the second (now the only enabled one) → 409, blocked
7. Delete confirmation requires typing the provider's exact name
```
