# Slice 1.6 — Staff screen (ops console)

## Goal

Staff holding `staff.manage` can see and manage everyone who can sign in to the ops console from
one screen under Govern: a table (email, role, authenticator enrolled, must-change-password, last
sign-in, created), an Add staff sheet (email, a role limited by ranking, an initial password with a
generate button, shown once), a Reset action (new initial password, ends sessions, removes the
authenticator — confirmed), and Revoke with an optional reason.

## Existing capabilities reused

- `GET/POST/DELETE /api/v1/staff` (WT-1) — this slice extends the same three routes rather than
  adding new ones. `POST` already both creates staff and resets an existing member's password
  (setting `initialPassword` on an existing email forces a password change, ends sessions and drops
  the authenticator — exactly what "Reset" needs), so the Reset dialog is the same call with the
  member's own current role and a freshly generated password.
- `staff_members.must_change_password` and `staff_users.two_factor_enabled` (ADR 0009 columns,
  already in migration `0003`/`0004`) — no migration needed for "must change password"/"2FA
  enrolled".
- The role-ranking rule already enforced server-side in `staff.ts` (`ROLE_RANK`) — the UI mirrors it
  only to avoid offering a control the API would 403 (agent-notes: hiding a control is not
  disabling it; the server re-checks regardless).
- `AUTH_LOGIN_SUCCEEDED` audit rows (WT-1's `auth/index.ts`) for "last sign-in", read via a
  correlated subquery keyed on `entity_type = 'user' AND entity_id = staff_members.user_id`.
- `sidebar-07`/`nav.ts` (one new line, `staff`, under Govern) and the existing table/sheet/dialog
  UI primitives (`components/ui/table`, `sheet`, `dialog`, `field`, `input-group`) — no new
  component system.

## Data changes

None. No migration. `GET /api/v1/staff` gains three additive fields
(`twoFactorEnabled`, `mustChangePassword`, `lastSignInAt`), all derived from existing columns.

## Authorization

Every route stays gated `requirePermission("staff.manage")` (unchanged). The admin-web route
(`/_app/staff`) additionally redirects away in its own `beforeLoad` when the signed-in session's
`permissions` doesn't include `staff.manage` — a client-side courtesy so a caller without the grant
never lands on a page that would only ever show `ErrorState`; the server-side gate is what actually
matters and is unchanged. Role ranking (grant no role above your own; act only on an account
strictly below your own) is the pre-existing `staff.ts` rule, untouched.

## Audit events

No new event types. `STAFF_ROLE_GRANTED`/`STAFF_PASSWORD_SET` (create/reset) and
`STAFF_ROLE_REVOKED` (revoke) are unchanged, except revoke now folds an optional `reason` into the
audit row's `after` when the caller supplied one.

## Tests

**Permission boundary** (existing, `staff.test.ts`): 401 anonymous, 403 for a caller without
`staff.manage`, 403 granting/acting above or at the caller's own rank.

**New (this slice, `staff.test.ts`):** the three new list fields — a freshly created member has
`lastSignInAt: null` and `mustChangePassword: true`; after a real password sign-in (no authenticator
registered yet, so it completes without a second factor), `lastSignInAt` becomes a timestamp; revoke
with a reason stores it only in the audit row's `after`, never on the `staff_members` row itself.

**Admin-web routing test** (`src/routing.test.ts`): `/_app/staff`'s `beforeLoad` throws (redirects)
for a session without `staff.manage` and does not throw for one that has it; `/_app/staff` is
confirmed to be a route nested under the ops console's own shell (`/_app`), and `/portal/*` is
confirmed to have zero overlap with that tree (see the tenant-portal slice doc for the other half
of that test file).

## Deviations

- **No new endpoint for Reset** — it is `POST /api/v1/staff` with the member's existing email/role
  and a fresh `initialPassword`, which the existing handler already treats as a full reset (password
  + forced change + authenticator drop + session end). Building a separate `/reset` route would
  duplicate that logic for no behavioural difference.
- **`lastSignInAt` reads `AUTH_LOGIN_SUCCEEDED`**, not a dedicated "last seen" column — there is no
  such column, and adding one would need a migration for a value the audit log already records
  faithfully (and cheaper: one indexed subquery, not a write on every sign-in).
