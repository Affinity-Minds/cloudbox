# Slice 6.4 — CloudBox Connect client

## Goal
A tenant member signs in with Tenant ID + email + a one-time code (no password, ADR 0009), sees only
the CloudBoxes they're authorized to reach, and presses one big **CONNECT** button to open an RDP
session — without ever seeing a network address, a managed Windows account name they didn't pick, or
a password.

## Existing capabilities reused
- Customer sign-in contract: `POST /api/auth/connect/send-code`, `POST /api/auth/connect/verify`
  (WT-14, ADR 0011/0009) — Connect adds no auth logic of its own, only a client for the fixed
  contract in `packages/contracts/src/connect.ts`.
- `GET /api/v1/connect/devices` (WT-14) for the device list; `mstsc.exe` for the RDP session itself.
- DPAPI (`System.Security.Cryptography.ProtectedData`) for local state, the same package the Agent
  uses (WT-4) — Connect uses **current-user** scope, not machine scope, because it is a per-user
  install with no admin.
- The entitlement envelope's key management scheme (`RSA-OAEP-256` / `A256GCM`, `jose` on the cloud
  side) is reused, not reinvented, for the RDP credential ciphertext (ADR 0013).

## Data changes
- `%LocalAppData%\CloudBox\Connect\session.bin` — DPAPI(current-user)-protected session (cookie,
  user, active tenant). Nothing machine-wide; uninstalling is deleting the exe and this one folder.
- Cloud: new table `rdp_session_grants` (migration `0013`, WT-11's own file, not `db/schema.ts` —
  see ADR 0013).

## API/contracts
- `POST /api/auth/connect/send-code {tenantCode, email}` → always `{success:true}`.
- `POST /api/auth/connect/verify {tenantCode, email, code}` → `{token, user, tenantId, tenantCode}`
  + `Set-Cookie`; `CONNECT_INVALID` (400) for anything wrong, identical for every cause.
- `GET /api/v1/connect/devices` → device list + tenant plan state. **Additive:** `ConnectDevice.lanAddress`
  (WT-11), sourced from the Agent's `network.lan_address` (also additive, `packages/contracts/src/agent.ts`).
- `POST /api/v1/connect/devices/:deviceId/session` (**new**, WT-11, ADR 0013) → `{deviceId, user,
  password, expiresAt}`; 403 not a member, 404 device/tenant mismatch, 409
  `no_active_subscription`/`device_not_enrolled`/`no_free_slot`.
- `HeartbeatResponse.commands` can now carry `{type:"SET_MANAGED_USER_PASSWORD", user,
  passwordCiphertext}` (documented for WT-10; not yet applied by the Agent).

## Authorization
- Every Connect API call after verify carries the session cookie; the cloud re-checks active tenant
  membership on every request (`GET /connect/devices`, `POST .../session`) — Connect holds no
  standing authority of its own.
- The RDP session grant is scoped to (device, tenant) and expires in 15 minutes; a revoked
  membership is refused on the very next call, not just hidden from a cached list.

## UI/Agent behavior
- Three screens (spec §59): Tenant ID + email → six-box code (auto-submit on the 6th digit, paste
  distributes across all six boxes, 30 s resend timer, honeypot field) → device list (name,
  Online/Offline pill, plain-English explanation for "no active plan" / "licence expired" /
  "offline", one CONNECT button per device, disabled unless online and licensed).
- Sign-out clears the local session file; a 401 from any authenticated call does the same
  automatically ("Your session has expired. Please sign in again.").
- RDP launch: `CredWrite` → `.rdp` file with no password field → `mstsc.exe <file> /f` → wait for
  exit → `CredDelete`, always (ADR 0013).

## Audit/events
- Cloud: `RDP_SESSION_GRANTED` (WT-11, new) — slot and expiry only, never the password or its hash.
- Existing `AUTH_LOGIN_SUCCEEDED {surface:"connect"}` (WT-1/WT-14) covers sign-in itself.

## Tests
- `apps/cloudbox-connect.tests`: sign-in state machine (send/resend/verify, identical error for every
  failure cause, session restore on startup, sign-out), session persistence round trip (real DPAPI,
  current-user scope, file never contains the cookie in the clear), device-list rendering for every
  state (online+licensed / offline / no plan / expired / both / empty), network abstraction
  (`LanDirect` resolves or explains a missing address; `NetBirdPlaceholder` always refuses), the
  credential write→launch→delete sequence around a fake `mstsc` (including on a launch failure, and
  that the password never appears in a launch argument or the `.rdp` file), and a real
  `CredWrite`/`CredDelete` round trip against the CI runner's own credential store.
- `apps/worker-api/test/rdp-session.test.ts`: membership boundary (403 non-member, 404
  wrong-tenant device), slot assignment (lowest free slot, skips one already granted, 409 once
  full, re-grants after expiry), and audit (no secret in `before`/`after`).

## Demo path
`docs/runbooks/connect-lab.md` — two machines on one LAN: the CloudBox (Agent + a managed user)
reports its `lan_address`; Connect signs in, sees it Online/licensed, presses CONNECT, and an RDP
session opens with no password ever visible.

## Rollback
Nothing server-side to roll back beyond the new table and route (both purely additive; no existing
endpoint's behavior changed). The client is a single self-contained exe with no installer state.
