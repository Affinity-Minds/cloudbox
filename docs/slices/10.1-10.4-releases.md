# Slices 10.1–10.4 — Release manifest, package signing, update channels, Pilot rollout (cloud side)

**Owner:** WT-18
**Status:** As built (cloud side only — the Windows updater that consumes this is a later slice)

## Goal

A staff operator can publish a signed OTA release for Agent/Status/Setup/Connect, roll it out through Development → Pilot → Stable channels (or Pinned overrides), gate promotion to Stable on real device health, and withdraw a bad release. A device can ask for the release assigned to it and report back a terminal install state. Master spec §18, §45, §50.

## Existing capabilities reused

- `ARTIFACTS` R2 binding (already provisioned) for the package object
- `requireDevice()` (WT-3, `src/devices/require-device.ts`) for the device-facing routes — imported, not modified
- `requirePermission("update.view"|"update.release"|"update.deploy")` (already in the seeded permission catalogue, migration 0003 — no permission-catalogue change needed)
- The `audit()` service, the screens pattern (`routes/v1/screens/*.ts`, ≤3 D1 round trips per `db.batch()` call), and the entitlement signing-key idiom (`ensureSigningKey` → `ensureReleaseSigningKey`, ADR 0004 → ADR 0012)

## Data changes (migration 0016)

- `releases(id, component CHECK(agent|status|setup|connect), version, channel CHECK(development|pilot|stable|pinned), manifest_json, manifest_jws, package_r2_key, package_sha256, package_size, min_agent_version, rollback_of, notes, status CHECK(draft|pilot|stable|withdrawn), created_by, created_at, promoted_at, withdrawn_at, withdraw_reason)`
- `release_assignments(id, release_id, scope CHECK(device|tenant|fleet_percent), device_id, tenant_id, percent, created_by, created_at)`
- `release_results(id, release_id, device_id, state CHECK(10 states — see §45), detail_json, reported_at)`
- `signing_keys` gains `purpose` (`entitlement`|`release`, default `entitlement`) via `ALTER TABLE ADD COLUMN` + BEFORE INSERT/UPDATE triggers (D1 cannot pair an `ALTER`-added column with an inline CHECK — same idiom as migration 0009's `plans.status`).

`rollback_of`/`notes`/`min_agent_version` are owner additions beyond the brief's literal table list, needed to store the full `ReleaseManifest` shape (`@cloudbox/update-contracts`) without a second JSON blob duplicating columns that already exist in `manifest_json`.

## New package `@cloudbox/update-contracts`

Mirrors `@cloudbox/licensing-contracts`'s shape for the *other* signer:

- `src/manifest.ts`: `ReleaseManifest` (zod), `MANIFEST_FORMAT` (`typ:"cbx-release+jwt"`, ES256), `signManifest`/`verifyManifest`, `ReleaseManifestError`
- `src/keys.ts`: `generateReleaseSigningKey`, `parseReleaseSigningSecret`
- `scripts/generate-signing-key.ts`, `scripts/make-test-vector.ts`
- `test/manifest.test.ts` (13 cases: schema validation, round trip, tamper of each JWS segment, wrong alg/typ/kid, malformed), `test/vector.test.ts` + committed `test/vectors/v1.json` — the fixed target for the Windows updater's .NET verifier, same acceptance model as ADR 0004/`licensing-contracts/test/vectors/v1.json`.

Unlike the entitlement, the manifest is **signed only** (JWS), never encrypted — it carries no secret. See ADR 0012.

## Server layout (`apps/worker-api/src/releases/`, all new, WT-18)

- `signing-key.ts` — `ensureReleaseSigningKey`, `releaseSigningKeyConfigured`, `activeReleaseSigningJwks`
- `upload.ts` — `storePackage`: streams a multipart `File` into R2 under `releases/<component>/<version>/<file>` (key generated server-side, never from the filename — agent-notes cloudflare-workers #18), hashing via `DigestStream` in the same pass; `MAX_PACKAGE_BYTES` (200 MB)
- `service.ts` — `createRelease`, `promoteRelease` (draft→pilot→stable with the health gate; stable↔pinned), `withdrawRelease`, `toRelease`
- `results.ts` — `recordResult`, `resultCounts`, `healthGatePassed`
- `assignments.ts` — `createAssignment`, `listAssignments`, `deleteAssignment`
- `resolve.ts` — `resolveAssignedRelease` (device > tenant > fleet_percent > channel default), `percentBucket` (deterministic `sha256(deviceId)`-derived 0–99 bucket)
- `download-token.ts` — short-lived HMAC-signed download URLs, proxied through the Worker (see "Deviations" — no S3-compatible credentials are provisioned for genuine R2 presigned URLs in this slice)

## API (as built, `/api/v1/releases`, mounted once in `routes/v1/index.ts`)

| Method | Path | Auth | Notes |
|---|---|---|---|
| POST | `/` | `update.release` | multipart (`file`, `component`, `version`, `channel`, `notes?`, `minAgentVersion?`, `rollbackOf?`); 413 over 200 MB (checked twice: `Content-Length` pre-check, then the parsed file's actual size); 409 `version_exists`; 503 `signing_key_unavailable` |
| POST | `/:id/promote` | `update.release` | `{channel}`; see ADR 0012's transition table; 409 `must_pilot_first` / `health_gate_failed` / `already_withdrawn` / `already_promoted` / `invalid_transition` / `must_be_stable_first` |
| POST | `/:id/withdraw` | `update.release` | `{reason}` 3–500 chars; 409 `already_withdrawn` / `not_released_yet` |
| GET / POST | `/:id/assignments` | `update.deploy` | `{scope, deviceId?, tenantId?, percent?}`; 409 `release_not_released` for a tenant/percent scope on a `draft` release (device scope is allowed on a draft — spec's "Internal lab" stage) |
| DELETE | `/:id/assignments/:assignmentId` | `update.deploy` | 404 unknown |
| GET | `/assigned?component=` | device Bearer (`requireDevice()`) | the highest applicable release for the caller's device (see resolution order below); 404 when none applies; `Cache-Control: no-store` |
| GET | `/:id/download?exp=&token=` | device Bearer | proxied R2 stream; the `exp`/`token` query pair is checked in addition to the Bearer (see "Deviations") |
| POST | `/:id/result` | device Bearer | `{state, detail?}`; audited `UPDATE_RESULT_REPORTED` |
| GET | `/screens/releases`, `/screens/releases/:id` | `update.view` | list with per-state result counts + assignment count; detail adds assignments, results, device/tenant pickers |

## Assignment resolution order (`resolve.ts`)

1. An explicit `scope='device'` assignment to the caller's device id.
2. An explicit `scope='tenant'` assignment to the caller's tenant id.
3. A `scope='fleet_percent'` assignment whose bucket (`percentBucket(deviceId)`, deterministic 0–99) is below the assignment's `percent` — raising the percentage only ever adds devices, never removes any.
4. The channel default: the newest release with `channel='stable'` **and** `status='stable'` for the component — moving a release to `channel='pinned'` removes it from this tier even though it stays `status='stable'`.

Within a tier, the newest `createdAt` wins. `withdrawn` releases are excluded from every tier.

## Health gate (Slice 10.4)

`healthGatePassed`: **≥1** `installed_healthy` result and **0** `installed_unhealthy`/`rolled_back` results, counted across every device that reported against the release. Checked only on the `pilot`→`stable` transition; `draft`→`pilot` and the `stable`↔`pinned` toggle have no gate.

## Audit events (as built)

- `UPDATE_RELEASED` — upload (draft created)
- `UPDATE_PROMOTED` — channel/status change via `/promote`
- `UPDATE_WITHDRAWN` — `/withdraw`
- `UPDATE_DEPLOYED` — assignment created or removed
- `UPDATE_RESULT_REPORTED` — a device's result report (actor `device`; not one of the brief's four named events, since it is device telemetry, not a staff action — see "Deviations")

## Ops UI (`apps/admin-web/src/routes/_app/updates.tsx`)

One route, no nested child route (unlike Subscriptions): the releases table drives an "Upload release" dialog and a detail `Sheet` (both client-side state). The detail sheet carries Promote/Withdraw actions (context-sensitive to the current `status`/`channel`), the assignment sub-panel (add/remove, scoped by device/tenant/percent pickers from the screen payload), and the results table. Terminal states render as coloured pills (`components/release-bits.tsx`) exactly as spec §45 lists them; a release with zero results shows "no results yet", never a fake zero row.

## Tests (`apps/worker-api/test/releases.test.ts`, 25 cases + `packages/update-contracts/test/*`, 13 cases)

Upload → R2 object + sha256 + a manifest that verifies against the signing key; oversized upload refused (both the `Content-Length` pre-check and a unit test of `storePackage`'s own size check, without allocating 200 MB); duplicate version refused; permission boundaries (support/read_only view but cannot mutate; admin can do everything super_admin can; a device Bearer cannot promote); health-gated promotion (passes with a healthy result, refused with an unhealthy one present, refused draft→stable directly, refused on a withdrawn release); assignment resolution precedence (device > tenant > channel default) and deterministic percent bucketing; a draft release visible only via an explicit device assignment; results recorded and reflected in the screen's per-state counts; the download route honours its short-lived token and 404s a withdrawn release even with a valid one.

## Deviations from the brief

- **`channel` vs `status`**: the brief gives both columns on `releases`; this slice treats them as distinct (rollout target vs. workflow gate) rather than redundant — see ADR 0012 for the full reasoning and the promotion transition table.
- **Fresh-TOTP step-up on promote-to-stable**: not enforced. No such helper is exported from WT-1's auth module yet; documented as a `TODO` in `service.ts` and a "Decision needed" below, per the brief's own "else document as TODO" instruction.
- **Download URL is proxied, HMAC-signed, not S3-presigned**: no S3-compatible access-key credentials are provisioned for R2 in this slice (only the `ARTIFACTS` binding), so a genuine presigned URL isn't possible. `download-token.ts` gets the same practical property — a URL that stops working on its own after 15 minutes — by deriving an HMAC key from the already-provisioned `RELEASE_SIGNING_JWK`'s private scalar; no new binding or secret was requested. The download route also re-checks the device's own Bearer token, so this is defence in depth, not the sole gate.
- **`UPDATE_RESULT_REPORTED`** is a fifth audit event, not one of the brief's four (`UPDATE_RELEASED`/`_PROMOTED`/`_WITHDRAWN`/`_DEPLOYED`): a device's own result report is telemetry, not a staff action, and forcing it into `UPDATE_DEPLOYED` would conflate "someone assigned a release" with "a device says what happened."
- **`packages/update-contracts`** is a new workspace package, requiring `apps/worker-api/package.json` and `pnpm-lock.yaml` edits (normally WT-0-only) and one line in `apps/worker-api/tsconfig.json`'s `paths` — same unavoidable pattern WT-5 recorded for `@cloudbox/licensing-contracts`.
- **Migration 0016**: generated via `drizzle-kit generate` against the current `src/db/schema.ts` (the committed meta snapshot already reconciles every prior migration back to 0011 — confirmed by re-running `generate` immediately after and getting "No schema changes"), then renamed from its auto-assigned number and hand-extended with the `signing_keys.purpose` trigger block (drizzle-kit cannot emit a CHECK for an `ALTER TABLE ADD COLUMN`).
