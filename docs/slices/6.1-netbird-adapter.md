# Slice 6.1 — NetBird controller adapter (cloud side, mocked server)

As built by WT-9 (`wt/p6-network-adapter`). Decision records: ADR 0007 (NetBird selection,
supersedes spec §4.8 Netmaker), ADR 0008 (standing support access).

## Goal

A thin, typed REST client over a self-hosted NetBird management server, plus desired-state
reconciliation from D1 → NetBird: one isolated group pair and policy per tenant, a standing
support-access policy reaching every tenant's servers, one-off setup keys minted on enroll and on
Connect network requests, and revocation wired into the existing device/membership revoke paths.
Built and tested against a fake NetBird server (`fetch` mock replaying the documented request/
response shapes); the real self-hosted server is provisioned separately
(`docs/runbooks/netbird-server.md`) and nothing here talks to it until `NETBIRD_API_URL` is set.

## Existing capabilities reused

- `audit()`, `newId()`/`nowIso()`, `createDb()` — no new plumbing.
- The dependency-injected `fetchImpl` seam already used by `email/providers/smtp.ts` (WorkerMailer)
  — `netbird.ts`'s client and every `network/controller.ts` export take an optional `fetchImpl`,
  defaulting to the global `fetch`, so tests never touch a real socket.
- `db.batch` for the Fleet detail Network tab query (WT-3's `loadFleetDetail`) — additive, same
  round trip.
- The `DEVICE_REVOKED`/`DEVICE_UNINSTALLED`/membership-revoke audit rows already written by their
  owners; this slice does not add a second audit row for the same action, only for its own two new
  writes (`NETWORK_SERVER_KEY_ISSUED`, `NETWORK_CLIENT_KEY_ISSUED`).

## Data changes (migration 0014, reserved)

`network_peers(id, kind CHECK('server','client','support'), tenant_id, device_id NULL, user_id
NULL, netbird_peer_id, netbird_setup_key_id, group_ids_json, status CHECK('not_configured',
'pending','active','revoked'), created_at, updated_at)`. One row per NetBird-mesh entity CloudBox
has provisioned:

- `kind: 'server'` — one per enrolled device (`device_id` set), the setup key/peer it was given.
- `kind: 'client'` — one per (tenant, user) Connect membership (`user_id` set), re-minting replaces
  it rather than creating a second row.
- `kind: 'support'` — one per tenant, a bookkeeping marker that this tenant's server group has been
  folded into the standing support policy. The `cbx-support` gateway peer itself is not
  tenant-scoped and has no row here (it is provisioned once, by hand, per the runbook).

Partial unique indexes enforce "one row per device", "one row per (tenant, user) client", and "one
row per tenant support marker" at the database level, not just in application code.

`netbird_peer_id` stays null until a future reconciliation job observes the real peer having
joined (out of scope here — the server is mocked); until then `status` stops at `pending` and
revocation (see below) falls back to revoking the unused setup key instead of deleting a peer.

## Files

- `apps/worker-api/src/network/netbird.ts` — the REST client: zod shapes for groups, policies
  (with rules), setup keys and peers; retry-with-backoff on 5xx (not on 4xx); the token only ever
  appears in the `Authorization: Token <token>` header, never logged or in a thrown error.
- `apps/worker-api/src/network/controller.ts` — reconciliation: `ensureTenantNetwork`,
  `ensureSupportAccess`, `mintServerSetupKey`, `mintClientSetupKey`, `revokeDevicePeer`,
  `revokeClientPeer`, `assertDefaultPolicyAbsent`, `deviceNetworkPeersQuery`.
- `packages/contracts/src/network.ts` (new) — `AgentNetworkInfo`, `ClientNetworkResponse`,
  `FleetNetworkPeer`, the peer kind/status enums.
- Additive contract fields: `EnrollResponse.network` (agent.ts), `FleetDetailScreen.network`
  (devices.ts).

## Naming (deviation from ADR 0007's shorthand — see "Deviations")

Groups and the tenant policy are named with the tenant's **public code**
(`cbx-server-CBX-00001`, `cbx-client-CBX-00001`, policy `cbx-tenant-CBX-00001`), not the internal
`ten_…` id, for readability in the NetBird dashboard. `cbx-support` and `cbx-support-access` are
global names, not per-tenant.

## API (additive only)

| Endpoint | Gate | Change |
|---|---|---|
| `POST /api/v1/agent/enroll` | token | 201 body gains optional `network: {setupKey, managementUrl}`; absent when NetBird is unconfigured or the mint failed (best-effort, never blocks enrollment) |
| `GET /api/v1/connect/devices/:deviceId/network` (new) | customer session, active membership in the device's tenant | 200 `{setupKey, managementUrl, expiresAt}`; 404 `not_found` (unknown device) or `network_not_configured`; 403 not a member. Audited `NETWORK_CLIENT_KEY_ISSUED` |
| `GET /api/v1/screens/fleet/:deviceId` | unchanged | `FleetDetailScreen.network`: this device's `network_peers` rows, newest first |
| `POST /api/v1/devices/:deviceId/revoke` | unchanged | now also calls `revokeDevicePeer` (best-effort) |
| `POST /api/v1/agent/uninstalled` | unchanged | `uninstallDevice` now also calls `revokeDevicePeer` |
| `DELETE /api/v1/tenants/:tenantId/memberships/:id` | unchanged | now also calls `revokeClientPeer` (best-effort) |

## Not configured (production today)

`NETBIRD_API_URL` is unset in `wrangler.jsonc` (WT-0 owns that file; see the handoff's "Requests to
WT-0"). Every controller entry point checks this first and, when unset: makes zero calls to
NetBird, writes/updates the `network_peers` row with `status: 'not_configured'`, and the enroll
response omits `network` entirely. Production behaviour is unchanged from before this slice.

## Deviations from the brief

- **Naming uses the tenant's public code**, not the internal id the ADR's own shorthand
  (`cbx-<tenant-id>`) implies — this slice's own Deliver bullet writes `cbx-client-<code>` /
  `cbx-server-<code>`, which reads as the public code; picked that reading for dashboard
  readability. Trivial to change (one function, `serverGroupName`/`clientGroupName` in
  `controller.ts`) if the owner prefers the internal id.
- **The Agent management port is a reserved placeholder (`7391`)**: nothing in the Windows Agent
  (Slices 2.1–2.5) listens on any network port today — it has a local named-pipe IPC and makes only
  outbound HTTPS calls. The brief asks for "TCP 3389 + the Agent management port" on both the
  tenant and support policies, so a port is reserved and wired into both rules, but it does not
  correspond to a real listener yet. See "Decisions needed" in the handoff.
- **`ensureTenantNetwork`/`ensureSupportAccess` self-heal, but do not poll**: a policy is only
  re-written (`PUT`) when its live rule set differs from the desired one, so repeated enrolls for
  an already-provisioned tenant cost one extra `GET /api/policies` each, not a write. An operator
  manually editing a CloudBox-owned policy in the NetBird UI (which ADR 0007 says not to do) would
  have their edit reverted on the next enroll for that tenant — that is intentional.
- **`ensureSupportAccess` derives destinations from NetBird's own group list** (every
  `cbx-server-*` group), not a second D1 cache of "which tenants have networks" — avoids a second
  source of truth for infrastructure D1 already causes to exist.

## Tests (`apps/worker-api/test/network/`)

- `fake-netbird-server.ts` — an in-memory server replaying the documented shapes; used as the
  injected `fetchImpl` everywhere in this slice (including the HTTP-level tests, where it patches
  the global `fetch` for the duration of each test — route handlers have no `fetchImpl` seam of
  their own).
- `netbird-client.test.ts` — request shape (token header, never in the URL/body), retry on 5xx,
  no retry on 4xx, network-error handling, the token never appearing in a thrown error.
- `network-controller.test.ts` — tenant network creation is idempotent; the generated policy JSON
  references only that tenant's own groups (isolation, asserted directly on the fake server's
  state); TCP 3389 + the management port, one-directional; Default-policy detection (throws, and
  `ensureTenantNetwork` propagates it); the support policy is present and grows with new tenants,
  idempotently; setup keys are one-off with the exact `auto_groups` and `expires_in`; revocation
  (peer delete when joined, setup-key revoke when not, safe to call twice); the not-configured path
  makes zero NetBird calls and records `status: 'not_configured'`; every mint audits.
- `network-wiring.test.ts` — HTTP-level: the enroll response's `network` field present/absent;
  the Connect network route's 401/403/404/200 boundaries and audit row; device revoke and
  membership revoke actually flip the `network_peers` row to `revoked`.

## Demo path (once the real VPS exists — see `docs/runbooks/netbird-server.md` §6 for the full
checklist; this is the short version against the mocked server, runnable today)

```
1. wrangler dev (worker-api), no NETBIRD_API_URL set → enroll a device → 201, no `network` field
2. Set NETBIRD_API_URL/NETBIRD_API_TOKEN in .dev.vars pointing at a real NetBird dev instance (or
   run the unit tests, which do this against the fake server) → enroll again → 201 with
   `network.setupKey`
3. Fleet → device detail → Network tab shows the row, status "pending"
4. Connect (customer session) → GET /connect/devices/:id/network → 200 with a client setup key
5. Revoke the device → Network tab shows "revoked"; NetBird's own setup key is revoked too
```

- Confirm (or replace) the reserved Agent management port (`AGENT_MANAGEMENT_PORT` in
  `network/controller.ts`, currently `7391`) once the Agent actually exposes a management surface
  over the mesh. Until then the port is inert — nothing listens on it, and the port appearing in a
  NetBird policy has no effect beyond that policy's own rule list.

  it embeds the NetBird Netclient (Slice 6.3).
