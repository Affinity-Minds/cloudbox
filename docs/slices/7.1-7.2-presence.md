# Slice 7.1–7.2 — Agent WebSocket channel + device presence (as built)

## Goal

Fleet dashboards read live device presence (online/offline, agent version, licence state, active
sessions) over a push channel instead of polling (spec §5.3, §16, §29). The heartbeat the Windows
Agent already sends every 60s (unchanged — see "Requests to another worktree") drives it; nothing
new is required of the agent for this slice.

## Existing capabilities reused

- `POST /api/v1/agent/heartbeat` (WT-3) — the only producer of presence data; this slice adds one
  best-effort call after it already writes D1, nothing else about the route changed.
- `audit()` service, `actor.type: "system"` (already a valid `AuditActorType`).
- `tenant_memberships` + `resolveFleetAccess`-style tenant scoping (WT-3's `screens/fleet.ts`) —
  `resolveRealtimeAccess()` in this slice is the same shape of check, for the same reason (no
  `:tenantId` path segment to hang `requireTenantStanding()` off).
- Cloudflare Durable Objects WebSocket Hibernation API and SQLite storage backend (no new
  dependency; both are Workers runtime features already reserved in `wrangler.jsonc`'s
  `FLEET_PRESENCE` binding and `exports.FleetPresence.storage: "sqlite"` from the foundation
  commit — this slice fills in the class, which was a 204-stub in `src/index.ts`).

## Data changes

**None.** No migration. Presence is entirely ephemeral, held in the `FleetPresence` Durable
Object's own SQLite storage (one `presence` table per instance) — it is rebuilt from the next
heartbeat/snapshot if ever lost, and is never the durable record of anything: D1's
`devices.last_seen_at` / `devices.last_health_json` (WT-3) and `audit_log` stay authoritative.
Reserved migration `0018` was not needed.

## Architecture

One Durable Object **class**, two roles, selected by request path rather than by anything the
instance introspects about itself (there is no such introspection):

- **`tenant:<tenantId>`** — one per tenant, **authoritative**. The heartbeat handler is the only
  thing that calls its `POST /presence`. It is the only place a `DEVICE_ONLINE`/`DEVICE_OFFLINE`
  audit row is written, and the only thing that runs the 60s offline-detection alarm.
- **`all`** — one, global, for staff. **Mirror-only**: every tenant instance forwards its own
  deltas to `all`'s `POST /presence/forward` (fire-and-forget, `ctx.waitUntil`). It never runs its
  own alarm and never writes an audit row — the tenant instance that first saw the transition
  already did, and duplicating it there would double-count the event.

Both roles serve `GET` WebSocket upgrades identically: `ctx.acceptWebSocket()` (Hibernation API,
so an idle Fleet tab does not keep the object billably alive), a `snapshot` message sent
immediately, then a `delta` per later change. `PresenceDevice`/`PresenceSnapshotMessage`/
`PresenceDeltaMessage` are in `@cloudbox/contracts` (`realtime.ts`).

**Offline detection:** the tenant instance arms a 60s alarm on its first heartbeat and re-arms it
after every alarm run while at least one device is still online; a device silent for 180s (3
missed heartbeats) is marked offline, broadcast, forwarded, and audited. Once nothing is online
the alarm stops rearming itself — the next heartbeat rearms it, so an all-offline tenant does not
pay for an alarm that would find nothing to do.

**Auth boundary (`routes/v1/realtime.ts`):** resolved entirely in the Worker, before the DO ever
sees the request, and never from anything the client supplies to the DO itself:

- Staff holding `device.view` → the global feed, or one tenant's with `?tenant=` (same filter the
  Fleet REST screen already offers staff).
- A customer → never the global feed. An explicit `?tenant=` must be one of their own *active*
  memberships (`forbidden` otherwise); with none given, their stored active tenant (`me.ts`,
  re-validated live) if still active, else their sole active membership. Several memberships and
  no explicit or stored choice → `tenant_required` (see "Deviations" in the handoff — a deliberate
  scope-down, not a gap).
- No session → `401`. Non-upgrade request from an authorised caller → `426`.

## API changes (as built, `/api/v1`)

| Method | Path | Auth | Notes |
|---|---|---|---|
| GET | `/realtime/fleet` `[?tenant=]` | staff (`device.view`) → global or one tenant; customer with active membership → their tenant | WebSocket upgrade (101); `426` without an `Upgrade` header; `400 tenant_required` for an ambiguous customer |
| POST | `/agent/heartbeat` | unchanged (Bearer device token, WT-3) | additive: after writing D1, best-effort `notifyHeartbeatPresence()` into the tenant's `FleetPresence` instance — never fails the heartbeat response if the DO errors |

## Presence document

```json
{
  "type": "delta",
  "device": {
    "deviceId": "dev_…",
    "online": true,
    "lastSeenAt": "2026-09-27T12:00:00.000Z",
    "agentVersion": "1.8.2",
    "licenseState": "active",
    "activeSessions": 3,
    "updatedAt": "2026-09-27T12:00:00.000Z"
  }
}
```

`licenseState` is the coarse `none`/`active` (never `expired` from this path — see "Deviations").
A `snapshot` message is `{ "type": "snapshot", "devices": [...] }`.

## Audit events

- `DEVICE_ONLINE` — written once per offline→online transition (including a device's very first
  heartbeat, treated as an implicit offline→online transition). Actor `{ type: "system", id:
  "fleet-presence" }`.
- `DEVICE_OFFLINE` — written once per online→offline transition, from the alarm. Never per
  heartbeat, never duplicated by the global mirror.

## UI (as built, admin-web)

- `hooks/use-fleet-presence.ts` — subscribes to `GET /api/v1/realtime/fleet`, reconnects with
  exponential backoff (1s → 30s cap), and disconnects entirely on `visibilitychange` while the tab
  is hidden (reconnecting on return). No polling anywhere in this path.
- `hooks/fleet-presence-reducer.ts` — the pure `applyPresenceMessage()` reducer, split out
  specifically so it is unit-testable without a WebSocket or a DOM.
- `routes/_app/fleet.tsx` — merges live presence into the REST-loaded rows by `deviceId`: `online`
  and `lastSeenAt` are overridden when the feed has heard about a device, and a new **Sessions**
  column (source: the feed only — the REST screen does not carry it, spec-listed field) renders
  "—" until it has. A small header badge ("Live" / "Connecting…" / "Offline") shows the socket's
  own state, separate from the REST loader's own refresh button. If the socket never connects
  (or the feed is briefly down), the page still renders exactly what the existing REST loader
  returned — nothing regresses to a spinner or an empty table.

## Tests

**worker-api** (`test/realtime.test.ts`, 13 cases):
- Presence upsert + WebSocket snapshot; a snapshot never includes `tenantId`.
- A connected socket receives a delta on the next heartbeat.
- `DEVICE_ONLINE` written exactly once across three repeated heartbeats.
- Offline after 3 missed heartbeats via `runDurableObjectAlarm()` (backdating `last_seen_at`
  directly in DO storage via `runInDurableObject()`, not a real 180s wait); `DEVICE_OFFLINE`
  written exactly once; the alarm does not reschedule itself once nothing is online.
- The global mirror receives a tenant instance's forwarded delta and never writes its own audit
  row.
- WebSocket auth boundary end to end through `app.request()`: anonymous → 401; a customer with no
  active membership → 403; a customer of tenant A asking for tenant B → 403 (never falls back to
  global); a customer of tenant A with no `?tenant=` → 101 on their own tenant; staff → 101 on
  global, or on one tenant with `?tenant=`; a non-upgrade request → 426; a real enrolled device's
  presence reaching a customer's snapshot end to end.
- `test/queries.ts` gained one entry (`resolveRealtimeAccess`'s tenant-membership lookup) for
  WT-6's query-plan regression test — same index as `screens.fleet`'s equivalent lookup.

**admin-web** (`hooks/fleet-presence-reducer.test.ts`, 5 cases): snapshot replaces the whole map;
a delta upserts one device without touching the rest; a delta for a device the map has never seen
adds it; applying the same delta twice is idempotent.

## Demo path

```
1. wrangler dev (worker-api) + vite (admin-web, proxies /api incl. WebSocket — vite.config.ts
   gained `ws: true` on the proxy, needed locally; production serves both from one Worker origin)
2. Sign in to Fleet as staff → header shows "Connecting…" then "Live"
3. Enroll a device, heartbeat it (curl, as in wt-p2-enrollment.md's demo) → Fleet row flips
   Offline → Online with no reload, Sessions column fills in from the heartbeat's
   `health.users.active_sessions`
4. Stop heartbeating that device → within ~60-180s (next alarm tick) the row flips back to
   Offline with no reload; `docs/handoffs/wt-p7-fleet-presence.md`'s audit query shows one
   DEVICE_ONLINE and one DEVICE_OFFLINE row, not a repeat of either
5. Hide the browser tab → reopen after a few seconds: header shows "Connecting…" briefly, then
   "Live" again, socket reconnected, no console errors
```

## Deviations

- **`licenseState` is coarse (`none`/`active`, never `expired`) on the presence document.** The
  Fleet REST screen's own `licenseState` (`none`/`active`/`expired`) needs `entitlements.valid_until`,
  which the heartbeat's existing `currentEntitlementForDevice()` read does not carry; adding a
  second D1 read on every heartbeat to get it would cost a round trip the hot path does not need
  (agent-notes fast-data-hydration.md's query-discipline). The REST loader remains the source of
  truth for the finer distinction; presence only needs a live coarse signal.
- **A customer with several tenant memberships and no explicit or stored `?tenant=`** gets
  `400 tenant_required` rather than an arbitrary pick. admin-web is staff-only today (no customer
  portal reads this endpoint yet, per `docs/handoffs/wt-p2-enrollment.md`'s own "Decisions
  needed"), so this path is exercised by tests, not yet by a real UI; a future customer portal
  should send `?tenant=` from its own active-tenant picker rather than rely on the fallback.
- **The WS auth boundary is one merged endpoint for both audiences** (`guard("either")`-style,
  matching `screens/fleet.ts`'s own precedent), not two separate staff/customer routes. The
  brief's test list mentioned "staff cookie on the customer route" as a boundary case; with one
  merged endpoint there is no literal separate "customer route" to send a staff cookie to, so
  that specific phrasing doesn't map onto this design — the boundary this slice actually tests is
  narrower but equivalent: a customer can never reach the global feed or another tenant's feed,
  full stop, regardless of the caller's session type.
