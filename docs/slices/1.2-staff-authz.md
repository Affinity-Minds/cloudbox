# Slice 1.2 — Staff authorization model

## Goal

CloudBox staff members (Super Admin, Admin, Support, Read Only) can be assigned fine-grained permissions. Every protected server-side operation enforces permissions; UI hints do not serve as security.

## Existing capabilities reused

- Permission catalogue seeded during foundation (from spec §7)
- `requirePermission(key)` middleware in Hono routes
- `staff_members` and `role_permissions` tables from foundation migration
- Drizzle for permission queries
- Audit service for permission changes

## Data changes

**Schema (from foundation migration 0003):**
- `staff_members(user_id, role CHECK('super_admin','admin','support','read_only'), created_by, created_at)`
- `permissions(key PK, description)` — seeded with spec catalogue (tenant.view, tenant.create, tenant.edit, etc.)
- `role_permissions(role, permission_key, PRIMARY KEY(role, permission_key))` — all mappings pre-seeded

**Permission catalogue (spec §7, seeded):**
- Super Admin: all permissions
- Admin: user.invite, tenant.*, subscriptions.view, audit.view, device.*, support_access.*
- Support: device.view, tenant.view, audit.view, support_access.request
- Read Only: audit.view, tenant.view, device.view

## Authorization

- Every route enforces `requirePermission('key')` server-side
- Super Admin receives every permission as rows (not a bypass)
- Permission checks are independent of UI rendering
- Tenant Owner standing != staff role (separate authorization model for tenant members)

## Audit events

- `PERMISSION_GRANTED` — user_id, permission_key, granted_by, timestamp
- `STAFF_ROLE_CHANGED` — user_id, old_role, new_role, changed_by, timestamp
- `PERMISSION_DENIED` — user_id, permission_key, route, timestamp (security event)

## Tests

**Happy path:**
- Admin user can create tenant (tenant.create)
- Admin user can view subscriptions (subscriptions.view)
- Support user can view audit (audit.view) but cannot create tenant

**Permission boundaries:**
- Read Only user cannot write anything
- Support user cannot manage subscriptions
- Any unauthorized route returns 403 with generic message
- No information leak on denied permission reason

**Negative tests:**
- Verify permission_denied events logged for unauthorized attempts
- Verify UI elements disabled for users without permission
- Verify cross-role confusion does not grant elevated access

## Demo path

```
1. Log in as Super Admin
2. Navigate to Staff Management (if UI built)
3. Verify all permission rows visible
4. Log out, log in as Support user
5. Navigate to Subscriptions — verify access denied or UI hidden
6. Check audit log for PERMISSION_DENIED events
```
