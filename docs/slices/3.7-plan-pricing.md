# Slice 3.7 — Plan pricing, add-on users, validity

## Goal

Plans carry a commercial price, and a subscription can buy extra managed users ("add-on users")
beyond the plan's base, at the plan's own per-add-on-user price, up to a plan-set cap. The device
entitlement's `max_managed_users` claim reflects the effective total (base + add-ons), not just the
plan's base. "Term" is relabelled "Validity" in the UI (the underlying field is still `termDays`,
unchanged from slice 3.6).

## Existing capabilities reused

- `plans`/`subscriptions` tables (slice 3.6's migration 0009, WT-14's migration 0010)
- The plan designer sheet/table, plan combobox (slice 3.6)
- WT-5's subscription create/edit dialog, entitlement issuer (`issueForDevice`)
- `audit()` service

## Data changes (migration `0011_plan_pricing.sql`)

Generated with `drizzle-kit generate` against a Drizzle schema change (not hand-written), then
renamed to the reserved number — `drizzle-kit generate` reports "no schema changes" again
afterward, confirming the snapshot/journal stayed in sync (verified before and after).

`plans` gains, all `ALTER TABLE ADD COLUMN` with constant defaults:

- `price_amount INTEGER NOT NULL DEFAULT 0` — minor units (paise/cents/…) of `currency`.
- `currency TEXT NOT NULL DEFAULT 'INR'` — ISO 4217; enforced to one of `INR/USD/EUR/GBP/AED` by
  `BEFORE INSERT`/`BEFORE UPDATE` triggers (D1/SQLite cannot pair an ALTER-added column with an
  inline CHECK — same idiom as migration 0009's `plans_status_check_*`).
- `addon_user_price_amount INTEGER NOT NULL DEFAULT 0` — minor units, per additional managed user
  per term.
- `max_addon_users INTEGER NOT NULL DEFAULT 0` — `0` = no add-ons allowed on this plan.

`subscriptions` gains:

- `addon_users INTEGER NOT NULL DEFAULT 0` — managed users bought beyond the plan's base, bounded
  at write time to the plan's `max_addon_users` (a data-dependent bound, not a DB CHECK).

## Effective limit and price (derived, never stored)

- **Effective managed-user limit** = `subscription.maxManagedUsers + subscription.addonUsers`.
  `subscription.maxManagedUsers` already resolves from the plan's base unless a subscription
  overrides it (an existing, unrelated feature); add-ons layer on top of whatever that resolved
  value is. Shared pure function: `effectiveMaxManagedUsers()` in `@cloudbox/contracts`.
- **Total price per term** = `plan.priceAmount + subscription.addonUsers * plan.addonUserPriceAmount`.
  Shared pure function: `totalPriceAmount()` in `@cloudbox/contracts`.
- Both are computed at read time by the screens loaders and by the entitlement issuer — nothing
  derived is written back to a row.

## API changes (as built, `/api/v1`)

- `POST /plans`, `PATCH /plans/:code` — `CreatePlanRequest`/`UpdatePlanRequest` gain
  `priceAmount`, `currency`, `addonUserPriceAmount`, `maxAddonUsers`. **All four are optional on
  create**, defaulting server-side to the column defaults (`0`/`'INR'`/`0`/`0`) — every plan
  created before this slice, and WT-8's own pre-written review test for it
  (`test/review/phase-2-verdict.test.ts`, "V2-5"), posts without them.
- `POST /tenants/:tenantId/subscriptions`, `PATCH /subscriptions/:id` — gain `addonUsers`
  (0–10,000, Zod-bounded). The plan-dependent bound (`≤ plan.maxAddonUsers`) is checked in the
  handler, not Zod: `400 {"error":"invalid_request","detail":"addon_users_exceeds_plan_max"}`.
  PATCH only re-fetches the plan when `addonUsers` is actually in the body, so the common PATCH
  (no `addonUsers`) keeps its existing round-trip count.
- `GET /screens/subscriptions`, `GET /screens/tenants/:tenantId` — each subscription row gains
  `effectiveMaxManagedUsers`, `totalPriceAmount`, `currency` (derived, see above); no extra D1
  round trip (an existing left-join query grew three more selected columns).
- License-key batches (`GET /license-keys`, WT-14) gain `planPriceAmount`/`planCurrency` on each
  batch — **for display only**: the plan's *current* price, shown so staff can see what a batch is
  "worth" at a glance; a batch never stores its own price and a redeemed subscription is never
  billed from it.
- Entitlement issuance (`issueForDevice`, WT-5's file, `apps/worker-api/src/entitlement/service.ts`)
  now selects `subscriptions.addonUsers` alongside the existing `maxManagedUsers`, and the claim's
  `max_managed_users` is `effectiveMaxManagedUsers(...)` instead of the bare column.

## UI (as built)

- Plan designer sheet (`components/plan-form-sheet.tsx`): Price (major-unit input, e.g. "99.00",
  converted to/from minor units at the form boundary) + Currency select; Add-on user price; Max
  add-on users; "Term (days)" relabelled **"Validity (days)"**.
- Plans table (`routes/_app/plans.tsx`): a Price column (`$99.00` (+ `$9.00`/user (≤20)` when the
  plan allows add-ons)); "Term" column relabelled "Validity".
- Plan combobox (`components/plan-select.tsx`): secondary line gains
  `· <price> / <validity>` (e.g. `2 devices · 6 users · $99.00 / 1 year`).
- Subscription create dialog (WT-5's `routes/_app/subscriptions.tsx`, additive) and the subscription
  detail's Edit dialog (`routes/_app/subscriptions.$id.tsx`): a new "Add-on users" field (bounded
  by the plan's `maxAddonUsers`, disabled at 0) plus a live-computed "Effective managed users" /
  "Total price (per term)" summary box.
- Subscription detail's summary table: "Managed users" row shows `14 (10 + 4 add-on)` when add-ons
  are in use; a new "Price (per term)" row.
- Tenant detail's Subscription tab (`routes/_app/tenants.$tenantId.tsx`): the same two — effective
  managed users with the add-on breakdown, and a Price/term column.
- Licence keys page (`routes/_app/licences.tsx`): a Price column on the batches table, titled to
  make clear it is the plan's current price, not what the batch was sold for.
- `components/plan-bits.tsx` gained `formatMoney` (uses `Intl.NumberFormat`'s currency style, so
  symbol/decimal placement is never hand-maintained per currency), `minorToMajorInput`.

## Tests

Workers pool, appended to `apps/worker-api/test/subscriptions.test.ts` (colocated with the existing
entitlement-issuance test infrastructure it reuses — real signing key, real RSA device, real
`verifyEntitlement` decrypt), 8 new tests: pricing fields default when omitted and store correctly
when given; invalid currency and negative/out-of-range pricing values rejected (400); `read_only`
403 on plan create; add-on users accepted within the plan's max; add-on users **above** the plan's
max refused on both subscription create and PATCH (`400 addon_users_exceeds_plan_max`); **the
entitlement claim's `max_managed_users` is the effective limit** (`6 + 4 = 10`, not the plan's bare
`6`); `effectiveMaxManagedUsers`/`totalPriceAmount`/`currency` appear correctly on the subscriptions
screen. All existing tests (including WT-8's own pre-written `test/review/phase-2-verdict.test.ts`
"V2-5" block for this exact slice) pass unmodified.

```
Staff console (super_admin):

1. Plans → New plan "CloudBox Team": 5 devices, 10 users, Validity 365, Price $99.00 USD,
   Add-on user price $9.00, Max add-on users 20 → Save
2. Plans table shows "$99.00 + $9.00/user (≤20)" and "1 year"
3. Tenants → New tenant "Team Org" → Plan combobox: "CloudBox Team · cloudbox-team" shows
   "5 devices · 10 users · $99.00 / 1 year" → pick it → Save
4. Subscriptions → New subscription → Team Org / CloudBox Team → Add-on users: 4 →
   "Effective managed users: 14", "Total price (per term): $135.00" (99 + 4×9) shown live →
   Create subscription
5. Subscription detail: "Managed users: 14 (10 + 4 add-on)", "Price (per term): $135.00"
6. Tenant detail → Subscription tab: the same two figures
```
