# Slices 5.3 / 5.4 — Parent account policy and managed user reconciliation

As built by WT-10. Spec §14.

## Goal

The server has exactly the remote Windows accounts the licence allows (`cloud01..cloudNN`, N = `max_managed_users`),
ready for the credential broker, and never loses an account or its data because a licence shrank or lapsed.

## Behaviour (`apps/cloudbox-agent/ManagedUsers/`)

- **Desired state** comes only from a **verified** lease (`LicenseSnapshot.MaxManagedUsers`). `NO_PLAN` (no lease) and
  `TAMPER` never change accounts. `EXPIRED`/`REVOKED` keep the last verified N (the gate blocks access instead).
- **When:** at service start (first cycle) and whenever the verified N changes. A failed reconcile is retried next cycle.
- **Create** (slot ≤ N, account absent): manifest `local_user cloudNN` (AccountManagement: disabled, random throwaway
  password, password never expires, user cannot change it) → manifest `local_group_membership CloudBoxUsers|cloudNN` and
  `Remote Desktop Users|cloudNN` (group name resolved from SID S-1-5-32-555, so localised Windows works) → a fresh random
  24-character password is set and stored DPAPI (machine scope) at `C:\ProgramData\CloudBox\credentials\cloudNN.bin`
  (folder SYSTEM + Administrators) for the credential broker (WT-11) → enabled.
- **Excess** (slot > N, CloudBox-owned, enabled) → **disabled**. Never deleted; profile and files untouched. Raising N
  again re-enables the same accounts with the same stored credential.
- **Not ours:** an account named `cloudNN` that is not a CloudBox manifest entry (created before Setup) is reported as a
  conflict and never touched (no password change, no group change, no enable/disable).
- **Parent account (5.3):** the console/maintenance account that ran Setup is never a `cloudNN`, never in
  `CloudBoxUsers`, never counted; the Status app autostarts only for it (logon task bound to its SID).
- **Uninstall** deletes the CloudBox-created accounts and the group (manifest), never their profile folders
  (`C:\Users\cloudNN` may hold customer work).

Health: `users: {configured, limit, active_sessions}` — configured = enabled CloudBox-owned accounts within N;
active_sessions = `WTSEnumerateSessions` sessions in `WTSActive` whose user is a `cloudNN` (console parent excluded).

## Tests

`ManagedUserTests`: 6 slots create cloud01..06 with both memberships, stored passwords, parent untouched; **6 → 4 disables
cloud05/06 and deletes nothing, then 4 → 6 re-enables without re-creating**; pre-existing `cloud02` is a conflict and
untouched; 0 slots disables all; slot parsing and active-session counting; password complexity.
`WindowsServerIntegrationTests.Managed_user_and_group_lifecycle_through_the_manifest`: real group + user + both
memberships through the manifest steps on `windows-latest`, enable/disable, revert, verify-clean.
