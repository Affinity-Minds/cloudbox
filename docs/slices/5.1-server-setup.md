# Slice 5.1 — CloudBox Server Setup (one customer-facing installer, self-service activation)

As built by WT-10 (`wt/p5-server-setup`). Decisions: ADR 0006 (manifest uninstall), ADR 0011 (self-service), ADR 0012
(RDP runtime).

## Goal

A customer double-clicks `CloudBox.Server.Setup.exe` on a Windows 10/11 Pro (or Server) PC, signs in with email + code,
picks or creates their organisation, confirms, and ends with a licensed CloudBox server: Agent service, Status app,
multi-session RDP runtime, Remote Desktop + NLA, managed users, licence gate, activation. Nothing upstream is visible.
Uninstall from Apps & Features returns the PC to its original state.

## Existing capabilities reused

- WT-4 install manifest (`ManifestRunner.Apply`, 14 step kinds, `Uninstaller`, `CleanVerifier`, `WellKnown`), CNG device
  key, DPAPI state, enrollment client, status pipe. Setup references the Agent assembly and runs the same code.
- WT-14 customer endpoints (exact sequence in `docs/slices/2.6-self-onboarding.md`), including `/start` for Turnstile.
- System.DirectoryServices.AccountManagement, Windows Firewall (netsh + HNetCfg COM), Task Scheduler XML, WebView2.

## Install plan (`apps/cloudbox-agent/Install/ServerInstall.cs`, order unit-tested)

| # | Step | Manifest entries (record-then-act) |
|---|---|---|
| 1 | prerequisites | — (x64, Windows 10/11 Pro/Enterprise/Education or Server; TPM presence reported, not required) |
| 2 | vcredist | `third_party_component vcredist-x64` (installs `/install /quiet /norestart` if missing or < 14.40; retained on uninstall) |
| 3 | agent | `registry_key HKLM\SOFTWARE\CloudBox`, `directory` ProgramData (SYSTEM+Admins) / Program Files\CloudBox / Agent, `file` Agent exe, `cng_key`, `event_log_source`, `service CloudBoxAgent`, `arp_entry` ("CloudBox Server", UninstallString = Agent `uninstall`) |
| 4 | status | `directory` Status, `file` each Status file, `scheduled_task "CloudBox Status"` (logon of the parent account, InteractiveToken, LeastPrivilege) |
| 5 | rdp-runtime | `third_party_component defender-exclusion:<vendor>`, `…:<RDP Wrapper>`, `directory` vendor, `file` rdpWrapper_x64.exe, `third_party_component rdp-runtime` |
| 6 | rdp-settings | `windows_setting` `fDenyTSConnections=0`, `RDP-Tcp\UserAuthentication=1`, `RDP-Tcp\SecurityLayer=2` (prior values kept); waits ≤ 30 s for the listener (warning if absent) |
| 7 | managed-users | `local_group CloudBoxUsers` (new kind), `directory ProgramData\CloudBox\credentials` |
| 8 | firewall-gate | `firewall_rule "CloudBox RDP Access"` (allow 3389), `firewall_rule "CloudBox RDP Gate"` (block 3389, enabled), `scheduled_task "CloudBox RDP Gate Watchdog"` |
| 9 | network | placeholder, records nothing (WT-9 installs the NetBird client here) |
| 10 | enrollment | — `POST /agent/enroll` with the grant; DPAPI state (+ cloud licence state/message, pinned signing keys from `GET /agent/signing-keys`); restart the service |
| 11 | health-check | — reads the pipe ≤ 3 min until licence evaluated and (when licensed) cloud01..cloudNN reconciled |

A failed step rolls back every recorded entry through the Agent's `Uninstaller` (cloud notified if enrollment already
happened). The Agent service later appends `local_user cloudNN` and `local_group_membership` entries when it reconciles;
`ManifestRunner.Apply` merges entries persisted by the other process before each write.

## Sign-in hand-off (WebView2 ↔ Worker)

Existing customers: native email → six-box code (`/api/auth/email-otp/send-verification-otp`,
`/api/auth/sign-in/email-otp`, `Origin` header = CloudBox origin, cookie jar in Setup only).

New customers, or a `403 challenge_required` step-up: Setup opens `{base}/start` in an embedded WebView2 (isolated
profile in `%TEMP%`, deleted after exit; top-level navigation confined to the CloudBox origin; no pop-ups, no devtools).
Turnstile runs in the real page. When the page's `POST /api/auth/start/verify` answers 200, Setup navigates the WebView
to `GET /api/v1/onboarding/setup/complete` (Worker, customer session required, `no-store`, nonce CSP), which posts
`{type: "cloudbox.setup.signed-in", email}` via `window.chrome.webview.postMessage`. Setup accepts it only from the
CloudBox origin, takes the HttpOnly session cookie from the WebView2 cookie manager (it never enters page script) and
continues natively. Without the WebView2 runtime, Setup says: create the account at `/start` in any browser, then sign in
here. After the activation grant is issued, Setup signs the session out.

## Organisation and activation

`GET /api/v1/onboarding/overview` (Owner/Admin tenants selectable) or new: `POST /onboarding/redeem` (licence key) /
`POST /onboarding/tenants` (name + IANA time zone, preselected from Windows). Confirmation text exactly: "Activate this
machine as a server for tenant CBX-xxxxx? Are you sure?". Then `POST /onboarding/activation-grants
{tenantId, deviceLabel: hostname}` → grant → the plan above.

Summary: Tenant ID, server name, licence (`licensed` → "Licensed (N days remaining)"; `no_active_plan` → "No active plan
found. Please contact the CloudBox admin."; `device_limit_reached` → its message), users ready, RDP state.

Silent: `CloudBox.Server.Setup.exe /S --enroll-token CBX-ENROLL-… [--base-url …]` (exit 0/1/2, log in `%TEMP%`).

## Worker additions (additive, WT-10)

| Method | Path | Gate | Purpose |
|---|---|---|---|
| GET | `/api/v1/agent/signing-keys` | device Bearer | public ES256 JWKs (`kid`, `alg`, `status`, `jwk{kty,crv,x,y,kid,alg,use}`); records the configured key first (idempotent) |
| GET | `/api/v1/onboarding/setup/complete` | customer session | WebView2 hand-off page |

Files: `apps/worker-api/src/routes/v1/setup.ts` (one line in `routes/v1/index.ts`), `routes/v1/agent.ts` (additive
route), `test/server-setup.test.ts`.

## Packaging

CI (`build-windows.yml`) publishes Agent and Status, downloads `rdpWrapper_x64.exe` and `vc_redist.x64.exe` by pinned
URL, refuses a SHA-256 mismatch (`third-party.lock.json`), stages `payload\{agent,status,vendor}` + notices and embeds it
(`-p:PayloadDir`). Setup is self-contained single-file, `requireAdministrator`; its WPF/WebView2 natives self-extract to
`%TEMP%\.net\CloudBox.Server.Setup`, removed a few seconds after exit. The installed Status app keeps its WPF natives next
to the exe (no self-extraction). Artifact `CloudBox.Server-win-x64`.

## Tests

`ServerInstallTests` (order, manifest completeness and safe ordering, secrets never in the manifest, rollback on failed
activation, unsupported Windows changes nothing, health-check waits, uninstall reverts every entry and verify-clean
passes, Status task only for the parent SID); `WindowsServerIntegrationTests` (real users/groups, firewall rule, Task
Scheduler XML on the runner); Worker `server-setup.test.ts`.
