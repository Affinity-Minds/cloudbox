# Slices 9.3-9.5 — Backups (cloud side): offsite upload/verify, retention policy data, dashboard

Cloud halves only (spec §56, Phase 9). Slices 9.1 (local application-consistent backup adapter),
9.2 (separate local target) and 9.6 (guided restore) are Windows Agent work, not built here — see
`docs/BACKUP_RESTORE.md` for the contract the Agent must satisfy.

## Goal

A device reports a backup job's lifecycle from local creation through cloud verification; the
cloud stores the artifact in R2 under `backups/<tenant>/<device>/...`, verifies its integrity by
recomputing a hash while streaming (never trusting the client's claim alone), retires artifacts on
a configurable per-tenant retention schedule (never the newest one, regardless of policy), and
gives staff an exceptions-first dashboard plus a per-device history and policy editor.

## Data changes (migration `0017_backups.sql`)

Hand-written (new tables, so a declarative `CHECK` is possible at `CREATE TABLE` time — unlike an
`ALTER TABLE ADD COLUMN`, see 0009/0011's trigger workaround for that case).

- `backup_policies(tenant_id PK → tenants.id, frequent_hours, daily_keep, weekly_keep,
  monthly_keep, yearly_keep, offsite_enabled, updated_by, updated_at)`. No row for a tenant means
  it follows the global default at `settings['backups.default_policy']` (seeded by this
  migration); `src/backups/policy.ts`'s `getEffectivePolicy()` is the one place this fallback is
  resolved.
- `backup_jobs(id, tenant_id, device_id, kind CHECK('frequent','nightly','manual','pre_upgrade'),
  state CHECK('created','verified_local','upload_started','upload_completed','cloud_verified',
  'retention_applied','failed'), started_at, finished_at, source_dataset, app_version, size_bytes,
  sha256, local_path_hint, error_json)`.
- `backup_artifacts(id, job_id UNIQUE, r2_key UNIQUE, size_bytes, sha256, encryption_json,
  uploaded_at, verified_at, retention_class CHECK('recent','daily','weekly','monthly','yearly'),
  expires_at, deleted_at, multipart_upload_id)`. `job_id` is unique — one artifact per job, created
  lazily on the first upload attempt. `multipart_upload_id` is an owner addition beyond the brief's
  column list, needed to resume a multipart upload across `parts`/`complete` calls.
- `restore_tests(id, tenant_id, device_id, artifact_id, performed_by, performed_at, outcome
  CHECK('success','failure','partial'), notes)`.

`packages/contracts/src/common.ts`'s `ID_PREFIX` gains `backupJob` (`bkj_`), `backupArtifact`
(`bka_`), `restoreTest` (`rst_`) — additive only.

## The state machine (`src/backups/state-machine.ts`)

Two transition tables, not one, because a client and the server are trusted differently:

- **Client-facing** (`PATCH /api/v1/backups/jobs/:id`): `created → verified_local` (requires
  `sha256`+`sizeBytes` in the same call — §23.8), `verified_local → upload_started`, and `failed`
  from any non-terminal state.
- **Server-only**: `upload_started/verified_local → upload_completed/cloud_verified` (the upload
  endpoints, only after a real hash match against a real R2 object) and `cloud_verified →
  retention_applied` (the retention sweep, once it has classified the artifact at least once).

A device can never PATCH its way to `cloud_verified` — that state is only reachable by actually
uploading bytes that hash-match the declared value.

## Upload (Slice 9.3)

- **Single-shot** (`POST /api/v1/backups/jobs/:id/upload`, ≤5 GiB, `MAX_SINGLE_SHOT_UPLOAD_BYTES`):
  the request body streams straight to `R2Bucket.put()` while a teed branch is hashed with the
  runtime's `DigestStream` (falls back to buffering + `crypto.subtle.digest` when the runtime
  doesn't expose `DigestStream` — true in `@cloudflare/vitest-pool-workers`'s bundled `workerd` as
  of this writing, agent-notes cloudflare-workers #15 "the pool often ships an older binary").
  A hash mismatch deletes the bad object and fails the job with `reason: "sha256_mismatch"`.
- **Resumable multipart**: `POST .../upload/init {sizeBytes, encryption?}` →
  `R2Bucket.createMultipartUpload()`; `PUT .../upload/parts/:n` (raw bytes) →
  `upload.uploadPart()`, returning `{partNumber, etag}` for the Agent to track; `POST
  .../upload/complete {parts, sha256, sizeBytes}` → `upload.complete()`, then one read-back of the
  assembled object to verify its hash (R2's multipart `complete()` has no whole-object hash of its
  own — known, documented cost).
- Object keys are always server-generated (`src/backups/r2-keys.ts`,
  `backups/<tenantId>/<deviceId>/<jobId>/<artifactId>.bin`) — never taken from client input
  (agent-notes cloudflare-workers #18).
- A device can only ever touch its own jobs: `loadOwnJob()` scopes every lookup to
  `deviceId = c.var.device.id` and returns 404 (not 403) for anything else.

## Retention (Slice 9.4, `src/backups/retention.ts`)

`classifyDeviceArtifacts()` is a pure function: grandfather-father-son rotation, one artifact
allowed per day/week/month/year period, each bucket exhausted (by count *and* by age horizon)
before an artifact rolls into the next one. Table-tested against fixed dates
(`test/backups-retention.test.ts`). `runBackupRetentionSweep()` is the Cron-driven (daily,
`src/scheduled.ts`) impure half: groups every live `cloud_verified` artifact by device, classifies,
persists `retention_class`/`expires_at`, deletes (R2 object + `deleted_at`) whatever is expired —
**except the single newest artifact per device, unconditionally** — and audits
`BACKUP_RETENTION_APPLIED` per device with deletions.

`src/scheduled.ts` is a new file (no other worktree had created one yet): a hook list run via
`Promise.allSettled` so one failing hook doesn't block another, wired into `src/index.ts`'s
default export via `Object.assign(app, { scheduled })` — chosen over replacing the default export
outright so every existing test's `app.request(...)` (Hono's own test helper) keeps working.
`wrangler.jsonc` gained one additive `triggers.crons` entry.

## Dashboard (Slice 9.5, §46)

- `GET /api/v1/screens/backups?tenant=&state=` (staff, `backup.view`): exception counts (devices
  protected/overdue — 48h without a verified cloud backup; failed jobs in the last 24h; restore
  verification overdue — no restore test within 90 days) computed from one batched query set (one
  D1 round trip), plus the primary table (`Tenant | Device | Last local backup | Last cloud backup
  | Verify | Retention | State`), exceptions sorted first.
- `GET /api/v1/screens/backups/:deviceId` (staff, `backup.view`): jobs, artifacts and restore-test
  history, plus the effective policy — two round trips total (device+tenant lookup, then a batch
  of the rest), inside the fast-data-hydration ceiling.
- `PATCH /api/v1/tenants/:tenantId/backup-policy` (staff, `backup.restore`): upserts the tenant's
  own policy row, audited `BACKUP_POLICY_UPDATED`.
- `POST /api/v1/backups/restore-tests` (staff, `backup.restore`): records a restore drill against a
  real artifact of the named device/tenant (validated, not trusted from the body alone), audited
  `BACKUP_RESTORE_TEST_RECORDED`.
- `GET /api/v1/me/backups` (customer, `requireUser()`): the caller's own tenant membership(s) only,
  read-only summary per device.
- admin-web: `routes/_app/backups.tsx` (exception cards + table), `routes/_app/backups.$deviceId.tsx`
  (Jobs/Artifacts/Restore tests/Policy tabs in a drawer), `components/backup-bits.tsx`,
  `api/backups.ts`. `nav.ts` gained one line (`backups`, under Operate).

## Deviations from the brief

- `multipart_upload_id` on `backup_artifacts`: not in the brief's column list, needed to resume a
  multipart upload across separate HTTP calls.
- Retention's "recent" window is a fixed 48h (`RECENT_WINDOW_HOURS`), independent of the policy's
  `frequentHours` (which governs how often Layer A backups run, not how long a recovery point is
  kept) — matches spec §23.7's literal "24-48 hours" example; the upper bound was chosen.
- The dashboard's "overdue" (48h) and "restore verification overdue" (90 days) thresholds are not
  in the spec as exact numbers; chosen as reasonable defaults and documented here for review.
- `POST /api/v1/backups/restore-tests` is staff-only for now — Slice 9.6 (guided restore, Windows
  side) does not exist yet to drive it from a customer-facing flow.
