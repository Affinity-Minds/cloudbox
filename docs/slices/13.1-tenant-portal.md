# Slice 13.1 — Tenant portal (customer-side administration)

## Goal

A tenant member signs in at `/login` (the existing closed customer OTP flow) and lands in a calm,
non-console portal under `/portal` scoped entirely to the tenants they belong to: their Tenant ID
and plan state (Home), their organisation's activated servers (CloudBoxes), who else can sign in
(Members), what they're paying for (Subscription, read-only), and a way to turn a machine into a
server for their organisation (Activate a server). A member of several tenants switches between
them from the header; nothing here can reach another tenant's data, and nothing here renders the
staff console's sidebar chrome.

Scoped down from spec §27's full navigation list (Home, CloudBoxes, Users, Sessions, Backups,
Subscription, Maintenance, Support, Audit) and §13.1's tenant-overview bullets (backup health,
maintenance notices, session tracking) to what the platform has actually built so far — no backup,
maintenance, network or session-tracking API exists yet (those are later phases, owned by other
worktrees). Adding tabs for unbuilt features would mean either dead links or fabricated data; per
agent-notes ux-patterns ("Honest empty states"), neither is acceptable, so this slice ships exactly
the five screens the brief asked for and leaves the rest for whichever worktree builds the
underlying capability.

## Existing capabilities reused

- The customer identity system and `/login` OTP flow (WT-1), unchanged.
- `requireTenantStanding('user'|'admin'|'owner')` (WT-1/WT-0 signature) as the server-side gate on
  every new route — the same fixed per-tenant gate the foundation contract specifies.
- WT-3's fleet loader (`loadFleet`), called directly (not through the staff-facing
  `/screens/fleet` query-string endpoint) so CloudBoxes reuses the exact same query and pills
  (`OnlinePill`, `KeyProtectionPill`, `LicenseStatePill`) as the ops console's Fleet screen.
- WT-2's membership CRUD (`POST/PATCH/DELETE /tenants/:tenantId/memberships`) and its standing
  ranking / last-active-owner guard — the portal's Members page is a new read (list) and a new UI,
  not a new write path.
- WT-14's `tenantPlanQuery`/`toTenantPlan` (plan state derivation) and the existing
  `POST /api/v1/onboarding/activation-grants` endpoint (Activate a server mints a grant through the
  same route the Setup app uses; no new server logic for issuing one).
- WT-5/WT-13's pricing helpers (`effectiveMaxManagedUsers`, `totalPriceAmount`, `formatMoney`) and
  UI pills (`SubscriptionStatusPill`, `ExpiryPill`, `KeyValue`).
- WT-2's tenant-switch mechanics (`GET /me/tenants`, `POST /me/active-tenant`) — the shell's header
  switcher is the same API, just relocated out of the old single-page portal.

## New surface

- **Server:** `apps/worker-api/src/routes/v1/portal.ts`, mounted at
  `/api/v1/tenants/:tenantId/portal` (one line in `routes/v1/index.ts`). Four `GET` routes, all
  gated `requireTenantStanding('user')` (any active member): `/` (Home), `/members`, `/devices`
  (delegates to `loadFleet` scoped to exactly this tenant), `/subscription`.
- **Contracts:** `packages/contracts/src/portal.ts` — `PortalHome`, `PortalMembersScreen`,
  `PortalMember`, `PortalSubscriptionScreen`, `PortalSubscription`. Additive; devices reuse the
  existing `FleetScreen`.
- **UI:** `apps/admin-web/src/portal/` gained a shell (`portal-shell.tsx`: header, tenant switcher,
  tab nav, sign out) and five page files (`home-page.tsx`, `cloudboxes-page.tsx`,
  `members-page.tsx`, `subscription-page.tsx`, `activate-page.tsx`), registered as child routes of
  `/portal` in `portal/router.tsx` (see "Deviations" below for why these are `createRoute` calls,
  not file-based routes).

## Data changes

None. No migration — every field this slice reads already exists (`tenants`, `tenant_memberships`,
`devices`, `subscriptions`, `plans`, `audit_log`).

## Authorization

Every route resolves the caller's tenant standing from `tenant_memberships` per request
(`requireTenantStanding('user')`), exactly like every other tenant-scoped route in this codebase —
never cached, never trusted from a path param alone. Reading is open to any active member (owner,
admin or user); mutations (invite, standing change, revoke) go through WT-2's existing
`memberships.ts` routes unchanged, which already enforce Owner/Admin-only + standing ranking + the
last-active-owner guard. The portal UI hides controls a caller's standing wouldn't be allowed to use
(a plain "user" never sees the standing `<select>` or "Add member"), but that is convenience, not
the gate — the same request from `curl` gets the same 403 the button would have.

## Audit events

No new event types. Reads are never audited (matching every other `screens/*` loader). Writes
still go through `memberships.ts` (`USER_INVITED`, `USER_STANDING_CHANGED`, `USER_REMOVED`) and
`self-service.ts` (`ENROLLMENT_TOKEN_CREATED` for an activation grant) — both extended in this
slice only to accept an optional free-text `reason` on revoke, folded into the audit row's `after`.

## Tests

**Tenant scoping (Workers pool, `apps/worker-api/test/portal.test.ts`):** a member of tenant A gets
403 on every one of the four routes for tenant B; Home's counts and Members' list only ever contain
tenant A's own rows; Devices matches exactly WT-3's fleet loader output for that tenant; Subscription
is `null` (not 404) for a tenant that never had a plan.

**Permission boundary:** anonymous is 401 everywhere; a staff session (no customer cookie) is 401,
never `setup_required` (customer-only routes, matching the existing convention for `/me`,
`/onboarding`, `/connect` — see the review test's `CUSTOMER_ONLY` predicate); a plain "user"-standing
member gets 403 on `POST /tenants/:tenantId/memberships` (cannot add a member).

**Query-plan registry:** six new entries in `apps/worker-api/test/queries.ts` (one per new query
shape), all resolving through an index, not a table scan.

## Deviations

- **Not file-based routes under `routes/portal/*`.** The customer surface is a second, code-based
  `createRouter` instance (`portal/router.tsx`), completely separate from the ops console's
  file-based generator that produces `routeTree.gen.ts` (see `main.tsx`'s "two surfaces, one bundle"
  comment and `ops-shell.ts`). Putting files under `src/routes/portal/*` would register them in the
  *ops console's* route tree instead — the two surfaces must never share one. The portal's own
  pages still live in their own files under `src/portal/`, registered with `createRoute()`, exactly
  as WT-1 already did for `/login`, `/start` and the old `/portal`.
- **`Link`/`useNavigate` avoided in every new portal file**, matching the pre-existing convention in
  `customer-login.tsx`/`start-page.tsx`/`tenant-cards.tsx`: TanStack's typed `Link` type-checks
  against the *globally registered* router (`main.tsx`'s `Register.router`, which is the ops
  console's), so a customer-only path fails to typecheck through it. Plain `<a href>` and
  `useRouter().history` are used instead, as already established.
- **Reason on revoke is a plain optional string**, not a picker — `packages/contracts/src/reasons.ts`
  does not exist on this base, so per the brief's own fallback this is a free-text field, kept only
  in the audit row.
- **`GET /tenants/:tenantId/portal/devices` bypasses the query-string `?tenant=` fleet endpoint**
  and calls `loadFleet` directly with access hard-scoped to exactly the path's `:tenantId`, so this
  route's only possible scope is the one `requireTenantStanding` already asserted — never the wider
  `?tenant=` a caller could otherwise pass.

## Requests to another worktree

- None blocking. When a network/backup/maintenance/support surface exists, its owner may want a
  portal tab of its own — the shell's `TABS` array in `portal-shell.tsx` is where to add it.
