# Slice 14.1-14.2 — Alerts, evaluator cron, notifications

## Goal

A stateful `alerts` table, evaluated every 5 minutes by a Cron Trigger, that answers "what is
broken now" without anyone watching a heartbeat feed: device offline, license expiring/expired, no
active plan, and (from the agent's last reported health) RDP/private-network/disk/reboot problems.
Staff see them on a new Alerts page and can acknowledge/resolve; a tenant's own members see their
own tenant's alerts in the portal API; warning/critical alerts email the tenant's contact and a
staff distribution list, with a 6-hour cooldown so nobody gets paged every 5 minutes for the same
problem.

## Existing capabilities reused

- `sendEmail(env, message, {purpose})` (WT-12) — provider fallback, audited attempts.
- `subscriptionLifecycle()` (WT-5, `entitlement/status.ts`) — the exact issuable/expiring/expired
  derivation subscriptions already use; the evaluator calls it rather than re-deriving expiry math.
- `audit()`, `newId()`, `nowIso()`, `requirePermission()`/`requireUser()`, the `settings` key/value
  table's upsert idiom (same pattern as `me.ts`'s `active_tenant:<userId>` row).
- `AgentHealth` (WT-3/4 contract) — read, not written; the evaluator never touches the heartbeat
  path.

## Data changes (migration `0015_alerts.sql`)

Generated with `drizzle-kit generate` against the Drizzle schema addition below (not hand-written);
a second `db:generate` reports "No schema changes, nothing to migrate", confirming the
snapshot/journal stayed reconciled.

`alerts` (new table):

- `id`, `tenant_id` (nullable FK `tenants.id`), `device_id` (nullable FK `devices.id`)
- `category` — CHECK against the full spec §25 list (15 values; only 8 are evaluated today, see
  "Categories evaluated" below)
- `severity` — CHECK `info|warning|critical`
- `status` — CHECK `open|acknowledged|resolved`, default `open`
- `dedupe_key` — **UNIQUE**, `${category}:${deviceId ?? tenantId}`. One row per dedupe key for the
  table's lifetime: a resolved alert's row is *reopened*, never re-inserted, when its condition
  recurs (a second INSERT would collide with the UNIQUE index on the old, resolved row — this is
  the actual reason for the design, not just tidiness).
- `opened_at`, `last_evidence_json`, `last_seen_at`, `acknowledged_by`, `acknowledged_at`,
  `resolved_at`, `notified_at`

Indexes: `(status, severity)`, `(tenant_id, status)`, `(device_id, status)`, plus the unique index
on `dedupe_key`.

## Evaluator (`apps/worker-api/src/alerts/evaluate.ts`)

Runs on the Cron Trigger (`wrangler.jsonc` `triggers.crons: ["*/5 * * * *"]`), via a `scheduled`
handler additively attached to the same object `src/index.ts` already exports as default (Hono app
instances are plain objects; `Object.assign(app, {scheduled})` mutates and returns `app` itself, so
every existing test's `app.request(...)` is untouched).

**Categories evaluated** (per the brief's explicit scope for these two slices):

- `device_offline` — `devices.last_seen_at` older than 10 minutes (or null) for `status='enrolled'`
  devices. Carries both `deviceId` and `tenantId` (dedupe is by device only).
- `license_expiring` / `license_expired` — tenant-scoped (`deviceId` null), from the tenant's
  newest non-cancelled subscription via `subscriptionLifecycle()`: `expiry === "expiring"` →
  warning, `"expired"` → critical.
- `no_active_plan` — an enrolled device with no live (unrevoked) entitlement *and* the tenant has
  no issuable subscription.
- `rdp_unhealthy`, `private_network_failed`, `reboot_required`, `disk_low` — parsed from
  `devices.last_health_json` (`AgentHealth`) when present. `rdp.state`/`network.state` outside
  `healthy`/`connected` (and not the literal `"unknown"`, which means "cannot determine yet", not
  "broken") open the first two; `updates.reboot_required` opens the third (severity `info`);
  `storage.free_bytes / storage.total_bytes` opens `disk_low` at the spec §24 thresholds (warning
  &lt;20% free, critical &lt;10%).

**Not evaluated** (valid rows the CHECK already accepts, belonging to phases not yet built):
`clock_tamper`, `device_binding_failure`, `backup_failed`, `backup_overdue`, `agent_outdated`,
`update_failed`, `break_glass_active`.

**Reconciliation, every tick:** compute the current problem set; for each, open (new row),
reopen (existing row was `resolved`), or refresh evidence (existing row still `open`/
`acknowledged`, no audit); for every currently-active row whose dedupe key is *not* in the current
set, resolve it. `ALERT_OPENED`/`ALERT_RESOLVED` are audited (`actor: system`, `source: cron`) only
on that transition — a re-detected, unchanged condition writes new evidence but no audit row, so
the log is not one entry per cron tick.

## Notifications (`apps/worker-api/src/alerts/notify.ts`)

On every tick, every currently **`open`** alert of severity `warning`/`critical` is a notification
candidate (an `acknowledged` alert has already been seen by a human and is not paged again; `info`
never pages). A candidate is *due* when `notified_at` is null or at least 6 hours old. Due
candidates email:

- the tenant's `support_contact_email` (falling back to `primary_contact_email`), and
- the staff distribution list, `settings` key `alerts.staff_recipients` (JSON array of emails),
  editable at Settings → "Alerts" (`settings.manage`).

A candidate with no resolvable recipient is skipped **without** spending the cooldown, so
configuring a contact later notifies promptly on the next tick rather than waiting up to 6 hours.
Every send audits `ALERT_NOTIFIED` with the recipient list and whether any provider actually
delivered it (`sendEmail`'s own per-attempt audit already covers provider-level detail).

## API changes (`/api/v1`)

| Method | Path | Gate | Notes |
|---|---|---|---|
| GET | `/screens/alerts?status=&severity=&tenant=` | `device.view` | `AlertsScreen`; one `db.batch` (list + facet counts) |
| POST | `/alerts/:id/acknowledge` | `device.manage` | 404 unknown, 409 `already_resolved`, idempotent if already acknowledged |
| POST | `/alerts/:id/resolve` | `device.manage` | 404 unknown, 409 `already_resolved` |
| GET | `/me/alerts` | customer session | The caller's active tenant memberships' open/acknowledged alerts |

`GET /me/alerts` is mounted at `/api/v1/me` from a **second** small router
(`routes/v1/me-alerts.ts`) — Hono's `.route()` just appends routes at a prefix (verified against
`hono-base.js`), so this does not touch WT-2's `me.ts`.

## Security assumptions

- Every route is gated server-side (`requirePermission`/`requireUser`), consistent with the rest of
  the API; `GET /me/alerts` re-resolves the caller's `tenant_memberships` per request, never trusts
  a client-supplied tenant id.
- The evaluator's actor is `system`/`alerts-evaluator`, distinguishable in the audit log from a
  staff acknowledge/resolve (`actor: user`) and from the cron's own transitions (`source: cron` vs
  `api`).
- Alert evidence (`last_evidence_json`) never contains secrets — it is derived from health-state
  strings, timestamps and byte counts, nothing from `entitlements.token` or credentials.

## Tests (`apps/worker-api/test/alerts.test.ts`, Workers pool, 15 tests, all green)

- Evaluator: opens once, reopens the *same* row on a second occurrence (dedupe by `dedupe_key`,
  not a duplicate insert), holds without re-auditing while the condition persists, resolves once
  when it clears — audited exactly once per transition, never per tick (idempotence test runs the
  evaluator three times with nothing changed and asserts no new audit rows).
- `no_active_plan`, `license_expiring`, `license_expired`, and all four health-derived categories
  (including a threshold check and a "no `total_bytes` ⇒ not evaluated" case for `disk_low`).
- Notification cooldown: notifies once on open, withholds on a same-hour re-run, notifies again
  once 7 hours have passed — asserted per alert id (not the evaluator's whole-DB return value),
  since the shared test D1 accumulates other tests' alerts too.
- `app.scheduled(...)` (via `cloudflare:test`'s `createScheduledController`) resolves without
  throwing.
- Permission boundaries: 401 anonymous, 403 `read_only` on every write route (acknowledge, resolve,
  settings PATCH); `device.view`'s 200 on the screen for `read_only` (per the seeded role catalogue,
  `read_only` holds every `*.view` key).
- Customer scoping: a tenant member sees their tenant's alert on `GET /me/alerts`; an unrelated
  signed-in user sees an empty list.
- Loader round-trip ceiling: `GET /screens/alerts` stays within 3 D1 round trips beyond auth
  (`countingD1`), matching the fast-data-hydration rule.

## Deviations from the brief

- **`AgentHealth.storage.total_bytes`** (optional, additive): the existing contract only had
  `free_bytes` (an absolute byte count). The brief's `disk_low` thresholds are percentages (§24:
  "warning below 20% free, critical below 10% free"), which cannot be computed from `free_bytes`
  alone. Added the minimal field needed to do the threshold check the brief asked for; `disk_low`
  is simply not evaluated for a device whose agent hasn't started sending it yet (older agents,
  covered by a dedicated test).
- **Two health-derived severities beyond warning**: `disk_low` is `warning` or `critical`
  depending on the threshold (both named in §24); `reboot_required` is `info` (not in spec's
  "critical examples" list, and pending a reboot is not itself an outage). Not specified verbatim
  by the brief; a reasonable reading of §44's severity baseline.
- **Query-plan registry** (`test/queries.ts`): not appended for the evaluator's own batch queries,
  which deliberately do unfiltered scans of `tenants`/`devices`/`entitlements` (a 5-minute
  background reconciliation over the whole fleet, not a per-request hot path — the
  fast-data-hydration ceiling and the query-plan regression test target request-path loaders). The
  two request-path additions (`screens/alerts.ts`, `me-alerts.ts`) join by primary key throughout
  and are covered by `alerts.test.ts`'s round-trip-ceiling assertion instead.
- **Notification model**: re-reading the brief's "cooldown per dedupe key (no repeat within 6h)"
  as *cooldown on repetition*, not *once ever* — an alert that stays open for days still reminds
  every 6 hours (silence for days on an unresolved critical alert seemed like the wrong reading).
  Documented for review if the intent was "notify on open only."
