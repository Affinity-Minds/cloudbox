## The RDP runtime we ship (owner has direct permission from the author for commercial bundling; evidence in private legal records)
Upstream: `https://github.com/sergiye/rdpWrapper`, release **2.15 (2026-06-12)**, C# .NET Framework 4.7.2 WinForms, single-file portable, no LICENSE file in the repo (permission covers it). Use the `rdpWrapper_x64.exe` asset. Verified from source (`Program.cs`, `Wrapper.cs`):
- Console mode is any argument: `rdpWrapper_x64.exe -install -offline`, `-uninstall -offline`, `-start`, `-stop`, `-generate`, `-help`. **Always pass `-offline` last** or it phones home to check for updates. Exit codes: 0 ok, 1 invalid args, -1 exception. Console output is also written by its FileLogger next to the exe.
- **Two traps.** (1) If the OS compatibility check fails in console mode it logs an error and exits **0**. (2) If another instance is running it shows a **MessageBox** even in console mode. So: never trust the exit code alone, kill stray instances first, run with a timeout, and verify the result by reading the registry.
- `-install` (default preferred wrapper **TermWrap**, Defender exclusion **on**): stops `TermService`, creates `C:\Program Files\RDP Wrapper\` with FullControl ACLs for SYSTEM, SERVICE and Users, adds a Defender exclusion for that folder if Defender is active, extracts `TermWrap.dll` + `zydis.dll` (+ `UmWrap.dll`, `EndpWrap.dll` on x64), sets `HKLM\SYSTEM\CurrentControlSet\Services\TermService\Parameters\ServiceDll` to the TermWrap path, restarts TermService. **No reboot.** TermWrap finds patch offsets automatically, so it survives Windows updates; it requires the **VC++ 2015–2022 x64 redistributable**.
- `-uninstall`: resets `ServiceDll` to `%SystemRoot%\System32\termsrv.dll`, stops TermService, deletes the folder, starts TermService.
- Detection (`CheckWrapperInstalled`): the file name in `ServiceDll` → `termsrv.dll` = not installed, `TermWrap.dll` = TermWrap, `rdpwrap.dll` = RdpWrap, anything else = third party; missing keys = unknown. `ImagePath` of TermService must contain `svchost.exe`.
- It does **not** touch `fDenyTSConnections`, NLA, or the firewall. Those are ours.
- Bundled upstream components and licences (WT-7 puts these in `THIRD_PARTY_NOTICES.md`): TermWrap, UmWrap, EndpWrap, RDPWrapOffsetFinder — llccd, **MIT**; rdpwrap.dll/ini — stascorp, **Apache-2.0**; Zydis — zyantific, **MIT**; sergiye/rdpWrapper — permission from author, no OSS licence.
- Known commercial risk: Defender and other AV vendors periodically flag RDP Wrapper binaries. Our installer must add the exclusion **before** extracting and must report `repair_required` when the DLL is quarantined, never silently fail.

## Deliver
1. **Acquisition, not vendoring.** CI (`build-windows.yml`) downloads `rdpWrapper_x64.exe` from the pinned release tag, verifies a SHA-256 you record in `apps/cloudbox-server-setup/third-party.lock.json` (tag, url, sha256, licence basis), and embeds it as a resource in `CloudBox.Server.Setup.exe`. Same for `vc_redist.x64.exe` (Microsoft, pinned URL + sha256). No binaries committed to git.
2. **`CloudBox.Server.Setup.exe`** (one customer-facing installer, `requireAdministrator`, self-contained win-x64, built on WT-4's `IInstallStep` manifest): prerequisites (Windows 10/11 Pro or Server, x64, TPM presence reported, VC++ redist installed silently `/install /quiet /norestart` if missing) → Agent service install (WT-4 code) → Status app install + per-user autostart for the parent account → **RDP runtime step** (`third_party_component` manifest entry): Defender exclusion, extract rdpWrapper exe to `C:\Program Files\CloudBox\vendor\`, run `-install -offline` with a 120 s timeout, verify `ServiceDll` ends with `TermWrap.dll`, verify TermService running and the listener up (`qwinsta` shows `rdp-tcp` listen, or `netstat` 3389 LISTENING) → Windows RDP settings step (`windows_setting` entries with prior values): `fDenyTSConnections=0`, NLA `UserAuthentication=1`, `SecurityLayer=2` → managed users step → firewall gate step → NetBird client step placeholder (WT-9 fills) → enrollment with the token from the CLI or an input dialog → first health check → summary screen. Every step reversible through the manifest; `uninstall` (WT-4) must run `-uninstall -offline` and restore every prior value. Silent mode: `CloudBox.Server.Setup.exe /S --base-url … --enroll-token …`.
3. **RDP adapter** in the Agent: `IRdpRuntime` with `Probe()` → normalized `healthy | wrapper_missing | service_stopped | listener_missing | unsupported_runtime | repair_required` from registry + service + listener + the DLL's existence and Defender quarantine state; `Repair()` re-runs the install step; reported in the health document `rdp` field. Do not let SaaS/UI depend on the upstream file names.
4. **Managed users** (Slice 5.4): desired state from the entitlement claim `max_managed_users` → local group `CloudBoxUsers` and users `cloud01..cloudNN` created with `System.DirectoryServices.AccountManagement` (same API rdpWrapper's `LocalUsersManager` uses), random passwords stored DPAPI-protected for the credential broker (WT-11), membership in `Remote Desktop Users`; excess users beyond the licence are **disabled, never deleted**; the parent console account is never counted. Reconcile on every entitlement change and every boot. All steps manifest-registered.
5. **Licence gate** (Slice 5.5): a CloudBox-owned Windows Firewall rule `CloudBox RDP Gate` on TCP 3389, scoped to the overlay subnet once WT-9 lands (any remote address until then), enabled only when the local verifier reports `VALID | OFFLINE_VALID | GRACE`; blocked for `EXPIRED | TAMPER | REVOKED`. Fail-closed on Agent crash: the rule's default state is block, the Agent opens it on each successful validation and a scheduled task re-blocks if the service is not running. Local console always works; never delete the runtime or users to enforce.
6. **Local verifier** (Slice 3.3): decrypt the stored compact JWE with the CNG key (`RSA-OAEP-256`/`A256GCM` via `Microsoft.IdentityModel.Tokens` + `System.IdentityModel.Tokens.Jwt`), verify ES256 with the pinned server public JWK from `signing_keys`, check `device_key_thumbprint` against the local key, check generation monotonic, evaluate validity with the trusted-time high-water mark, publish the normalized licence state to the pipe and the health document.
7. **Status app** (Slice 2.4/3.5 minimum): WPF, appliance-like, reads the pipe: device, tenant, licence state and days remaining, configured slots vs active sessions (`WTSEnumerateSessions`), RDP runtime state, network placeholder, renewal QR when within warning days (QR from a maintained library, content is a public renewal URL only).
8. Tests: adapter state machine from faked registry/service/listener inputs; managed-user reconciliation from N=6 to N=4 disables not deletes; gate rule state per licence state; verifier rejects wrong-device token, tampered token, stale generation. Physical acceptance by the owner from `docs/runbooks/rdp-runtime.md`: install on the lab PC → two RDP sessions from two accounts on the LAN at once → Fleet shows 2 active sessions → expire the licence in the console → new session blocked, existing session and console untouched → uninstall → `verify-clean` exits 0 and `ServiceDll` is back to `termsrv.dll`.

Demo path: `CloudBox.Server.Setup.exe --base-url https://box.affinityminds.in --enroll-token CBX-ENROLL-…` on the lab PC → summary shows every step green → `mstsc` from a second PC on the LAN to `cloud01`, then `cloud02` simultaneously → Status shows 2/6 active → Fleet detail shows the same → screenshot both.
